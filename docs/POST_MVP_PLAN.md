# supervisor-rs — POST_MVP_PLAN

Функциональность, намеренно вырезанная из MVP. Здесь — nice-to-have, к которому
можно вернуться после того, как ядро (Этапы 1–5) работает и покрыто тестами.
Ничего из этого не входит в v1.

## Ротация логов

- Захват stdout/stderr супервизируемых процессов в файлы вместо наследования
  дескрипторов супервизора.
- Ротация по размеру и/или времени, ограничение числа хранимых файлов,
  опциональное сжатие. Возможна интеграция с внешним `logrotate` через SIGHUP.

## cgroups / resource limits

- Помещение супервизируемого дерева в cgroup v2 для реальных лимитов CPU/памяти
  и надёжного «убить всё дерево одним махом» (`cgroup.kill`), что строже, чем
  `killpg`.
- `setrlimit` для per-process лимитов (RLIMIT_NOFILE, RLIMIT_AS, RLIMIT_CPU).
- Linux-специфично — потребует отдельной ветки кода и деградации на не-Linux.

## Прочие идеи

- Зависимости между процессами (стартовать B только после того, как A готов).
- ~~Перезагрузка конфига без рестарта демона (SIGHUP → diff → применить).~~ —
  **реализована в Этапе 8** (см. `docs/TECHNICAL_PLAN.md`): по SIGHUP демон
  перечитывает тот же файл, diff по имени процесса, применяет только разницу
  (добавить / убрать / рестартнуть изменённый), «всё или ничего» при битом
  конфиге. С оговорками, остающимися кандидатами здесь же: **только SIGHUP** —
  команды `reload` в control-socket нет; `done`-процесс reload не оживляет;
  изменение конфига user-stopped процесса не запускает его (оператор побеждает);
  неудавшийся spawn добавленного процесса не ретраится (best-effort, как в
  `new()`).
- `notify`-протокол готовности (аналог `sd_notify`) для точного момента «готов».
- Экспорт метрик (рестарты, uptime, коды выхода) в формате Prometheus.
- ~~Полноценный control-socket с командами `start`/`stop`/`restart <name>`~~ —
  **реализован в Этапе 6** (см. `docs/TECHNICAL_PLAN.md`), с оговоркой:
  предположение «а с ним и переход цикла на событийную модель» не
  подтвердилось — по решению пользователя сокет встроен в тот же поллинговый
  `run()` через неблокирующий `accept` раз в тик, `signalfd`/self-pipe не
  вводились. Из v1 Этапа 6 осознанно вынесены: `status`/список процессов через
  сокет, оживление терминально завершившегося (`done`) процесса, различение в
  `status` «остановлен оператором» vs «завершился сам», параллельная обработка
  нескольких клиентов за один тик, аутентификация сверх прав каталога 0700,
  `--instance` (несколько демонов на uid) — эти пункты остаются кандидатами
  здесь же, в POST_MVP.
