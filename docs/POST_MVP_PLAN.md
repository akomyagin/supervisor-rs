# supervisor-rs — POST_MVP_PLAN

Функциональность, намеренно вырезанная из MVP. Здесь — nice-to-have, к которому
можно вернуться после того, как ядро (Этапы 1–5) работает и покрыто тестами.
Ничего из этого не входит в v1.

## Ротация логов

~~Захват stdout/stderr супервизируемых процессов в файлы вместо наследования
дескрипторов супервизора; ротация по размеру, ограничение числа хранимых
файлов.~~ — **реализовано в Этапе 9** (см. `docs/TECHNICAL_PLAN.md`):
опциональная секция `[process.log]` на процесс задаёт `stdout-path`/`stderr-path`
(раздельные файлы, хотя бы один обязателен), `max-size-bytes` (default 10 MiB) и
`keep` (default 5). Захват — через pipe и по потоку ОС на поток вывода;
ротация — по размеру, в момент записи, полностью внутренняя (без сигналов,
внешних инструментов и интервальных таймеров).

**Интеграция с внешним `logrotate` через SIGHUP отклонена**: SIGHUP с Этапа 8
занят перезагрузкой конфига (`src/signal.rs::RELOAD_PENDING`), а второй смысл
тому же сигналу давать нельзя — у logrotate-конвенции сигнал фиксирован именно
как SIGHUP, так что правило «каждый качественно новый смысл сигнала — свой флаг»
здесь не спасает. Ротация сделана полностью бессигнальной и внутренней.

Осознанно вынесены из v1 Этапа 9 и остаются кандидатами здесь же: сжатие
ротированных файлов; ротация по времени (v1 — только по размеру, чтобы не
заводить второй, реальный таймер вне `Clock`/`FakeClock`); границы ротации по
строкам (сейчас — по границам чанков `read()`, строка может разъехаться между
`.1` и текущим файлом); видимость лог-путей в `status`/state-файле.

## cgroups / resource limits

~~Помещение супервизируемого дерева в cgroup v2 для реальных лимитов CPU/памяти;
`setrlimit` для per-process лимитов (RLIMIT_NOFILE, RLIMIT_AS, RLIMIT_CPU).~~ —
**реализовано в Этапе 10** (см. `docs/TECHNICAL_PLAN.md`): опциональные секции
`[process.rlimit]` (`nofile`/`as-bytes`/`cpu-secs`, `setrlimit` в `pre_exec`,
`soft = hard`) и `[process.cgroup]` (`cpu-max-percent`/`memory-max-bytes`, cgroup
v2 на всё дерево, корень задаётся флагом `--cgroup-root`). Неудача настройки
cgroup — ошибка спавна процесса (честно, не тихая деградация); cgroup-директории —
служебный артефакт рантайма, убираются при штатном выходе демона.

Деградация на не-Linux оказалась **не** отдельной компайл-таймовой веткой:
`setrlimit` POSIX, а cgroup-код — `std::fs` по путям, поэтому на не-Linux (или
Linux без cgroup v2) настройка cgroup падает в рантайме ошибкой IO → та же
политика «процесс не стартует». Деградация есть — но рантаймовая и громкая
(ошибка спавна), а не компайл-таймовая.

Осознанно вынесены из v1 Этапа 10 и остаются кандидатами здесь же:

- **`cgroup.kill` как teardown строже `killpg`** — **осознанно НЕ сделан, решение
  пользователя.** Этап 10 использует cgroup ТОЛЬКО для лимитов CPU/памяти;
  механика Этапа 4 (`killpg`, peek → sweep → reap) остаётся единственным
  механизмом остановки и не тронута. Сбежавший из process-группы собственным
  `setsid` орфан (известное ограничение Этапа 4) остаётся в cgroup и был бы
  достижим для `cgroup.kill` — но это отклонено; кандидат на будущее.
- раздельные soft/hard у rlimit (v1 — `soft = hard`, сценария «процесс сам
  поднимает себе soft» у супервизируемых демонов нет);
- `clone3(CLONE_INTO_CGROUP)` для атомарного помещения ребёнка в cgroup (закрыл
  бы окно «exec → attach»; отклонён как непропорциональная сложность);
- другие контроллеры (io, pids); `cpu.max` с настраиваемым period (v1 — фикс.
  100 ms, `cpu-max-percent` как один knob);
- видимость лимитов/cgroup-пути в `status`/state-файле (v1 — не в снапшоте, схема
  `version = 1` не меняется; наблюдаемо через cgroupfs и `/proc/<pid>/limits`).

## Health-checks сверх «процесс жив»

~~В MVP «жив» = процесс существует. Активные проверки — exec-проба (запустить
команду, успех по коду выхода), TCP-проба (порт принимает соединение),
HTTP-проба (эндпоинт возвращает 2xx). Порог неуспехов → рестарт даже живого,
но «залипшего» процесса.~~ — **реализовано в Этапе 7** (см.
`docs/TECHNICAL_PLAN.md`), одна проба на процесс, конфигурируемая секцией
`[process.health-check]`. С оговоркой: **startup/liveness/readiness различия
по мотивам systemd/k8s не подтвердились** — по решению пользователя v1 несёт
только одну liveness-пробу (порог неуспехов → рестарт), а роль startup-пробы
исполняет `start-period-secs` (задержка перед началом счёта, аналог k8s
`initialDelaySeconds`). Из v1 Этапа 7 осознанно вынесены и остаются
кандидатами здесь же: hostname/DNS в `host` (только `IpAddr` поддержан),
несколько проб на процесс, видимость health-состояния и причины рестарта
(оператор vs health) в `status`, TLS/редиректы/chunked/keep-alive у HTTP-пробы,
полноценная startup/readiness-триада.

## Прочие идеи

- Зависимости между процессами (стартовать B только после того, как A готов).
- ~~Перезагрузка конфига без рестарта демона (SIGHUP → diff → применить).~~ —
  **реализована в Этапе 8** (см. `docs/TECHNICAL_PLAN.md`): по SIGHUP демон
  перечитывает тот же файл, diff по имени процесса, применяет только разницу
  (добавить / убрать / рестартнуть изменённый), «всё или ничего» при битом
  конфиге. С оговорками, остающимися кандидатами здесь же: **только SIGHUP** —
  команды `reload` в control-socket нет; `done`-процесс reload не оживляет;
  изменение конфига user-stopped процесса не запускает его (оператор побеждает);
  неудавшийся spawn добавленного процесса не ретраится (best-effort, как в
  `new()`).
- `notify`-протокол готовности (аналог `sd_notify`) для точного момента «готов».
- Экспорт метрик (рестарты, uptime, коды выхода) в формате Prometheus.
- ~~Полноценный control-socket с командами `start`/`stop`/`restart <name>`~~ —
  **реализован в Этапе 6** (см. `docs/TECHNICAL_PLAN.md`), с оговоркой:
  предположение «а с ним и переход цикла на событийную модель» не
  подтвердилось — по решению пользователя сокет встроен в тот же поллинговый
  `run()` через неблокирующий `accept` раз в тик, `signalfd`/self-pipe не
  вводились. Из v1 Этапа 6 осознанно вынесены: `status`/список процессов через
  сокет, оживление терминально завершившегося (`done`) процесса, различение в
  `status` «остановлен оператором» vs «завершился сам», параллельная обработка
  нескольких клиентов за один тик, аутентификация сверх прав каталога 0700,
  `--instance` (несколько демонов на uid) — эти пункты остаются кандидатами
  здесь же, в POST_MVP.
