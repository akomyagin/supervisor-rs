# supervisor-rs — PLAN

## Видение

`supervisor-rs` — минимальный супервизор процессов (мини-systemd) для Unix.
Демон читает конфиг-файл со списком процессов, стартует их, следит за ними и
перезапускает согласно policy (`always` / `on-failure` / `never`), а при
собственном завершении корректно и предсказуемо гасит все дочерние процессы —
включая внуков, которых дочерний процесс форкнул сам.

Проект учебный, соло-разработка с AI-ассистентом, бюджет $0. Цель — не бизнес,
а искренняя техническая сложность: аккуратная POSIX-механика управления
процессами, сигналами и process-группами.

### Почему Rust

Это **первый Rust-проект в портфеле**, и тема выбрана под язык не случайно.
Управление процессами в Unix — это работа на границе с ядром: `fork`/`exec`,
доставка сигналов, process groups, реапинг зомби через `waitpid`. Здесь важен
низкоуровневый контроль над FFI к libc при сохранении безопасности памяти и
явной обработки ошибок — ровно то, что Rust даёт «из коробки» через крейт `nix`
(безопасные обёртки над сигналами и syscalls) и через `Result`-ориентированный
стиль. Практика системного программирования на Rust — основная учебная ценность
проекта.

## Архитектура (верхнеуровнево)

```
config-файл (TOML)
      │
      ▼
  config::load ──► Vec<ProcessConfig>
      │
      ▼
  supervise loop (process.rs)
      ├─ spawn: каждый процесс — в своей process-группе (setsid)
      ├─ monitor: waitpid, реапинг зомби, определение факта смерти
      ├─ restart: policy + exponential backoff
      └─ shutdown: SIGTERM группе → grace timeout → SIGKILL группе → reap
      ▲
      │ SIGTERM / SIGINT супервизору
   signal handler ──► форвардит сигнал детям
```

Ключевые технические инварианты:

- **Дерево, а не один child.** Каждый супервизируемый процесс запускается в
  собственной process-группе; сигналы шлются группе (`killpg`), поэтому внуки
  тоже получают SIGTERM/SIGKILL, а не остаются осиротевшими.
- **Никаких зомби.** Любой завершившийся потомок реапится через `waitpid`.
- **Graceful-then-forceful shutdown.** Сначала SIGTERM и вежливое ожидание,
  затем — SIGKILL по таймауту. Это единая точка, которую проект и существует
  чтобы сделать правильно.

## Этапы

- **Этап 0 — Bootstrap.** Скелет проекта: `cargo init`, зависимости-заглушки,
  модули `config`/`process` с `TODO(Этап N)`, документация. `cargo check`
  проходит чисто. (Готово.)
- **Этап 1 — Конфиг + базовый spawn.** Парсинг TOML-конфига со списком
  процессов; запуск процессов без рестарта. (Готово.)
- **Этап 2 — Restart policy + backoff.** `always` / `on-failure` / `never`,
  реапинг зомби, экспоненциальный backoff между рестартами. (Готово.)
- **Этап 3 — Форвардинг сигналов.** Перехват SIGTERM/SIGINT у супервизора и
  проброс их дочернему процессу. (Готово.)
- **Этап 4 — Process groups + деревья процессов.** `setsid`/`killpg`, корректный
  каскад SIGTERM → таймаут (`stop-grace-secs`) → SIGKILL для всего дерева.
  (Готово.)
- **Этап 5 — CLI статуса.** Подкоманды `run <config>` и `status`; демон
  публикует снапшот процессов (имя, состояние, PID, число рестартов, uptime) в
  файл состояния, `status` его читает и печатает. Управляющие подкоманды
  (`start` / `stop` / `restart <name>`) и control-socket остались за рамками
  MVP — см. Этап 6. (Готово.)
- **Этап 6 — Control-socket.** Первый пост-MVP этап. Демон слушает
  unix-domain-socket и принимает подкоманды `start <name>` / `stop <name>` /
  `restart <name>` на работающем экземпляре, без его перезапуска: `stop`
  останавливает супервизируемый процесс и подавляет для него restart policy,
  `start` возвращает остановленный в супервизию, `restart` принудительно
  пересоздаёт работающий. (Готово.)
- **Этап 7 — Health-checks.** Активные проверки здоровья вместо простого «peek
  по pid»: опциональная секция `[process.health-check]` конфигурирует одну
  пробу на процесс — exec (код выхода), tcp (соединение принято) или http
  (2xx). `failure-threshold` неуспехов подряд форсирует рестарт живого, но
  «залипшего» процесса через ту же машину TERM → grace → SIGKILL, что и
  операторский `restart`. (Готово.)
- **Этап 8 — Перезагрузка конфига (SIGHUP).** По `kill -HUP <pid>` демон
  перечитывает тот же файл, сравнивает список процессов по имени и применяет
  только разницу: добавляет новые, останавливает и удаляет убранные,
  принудительно рестартит изменённые, неизменённые не трогает. Битый новый
  конфиг отклоняется целиком — «всё или ничего», демон продолжает жить на
  старом. Без рестарта демона и без teardown всех деревьев. (Готово.)

Подробная техническая разбивка по этапам — в `docs/TECHNICAL_PLAN.md`.
