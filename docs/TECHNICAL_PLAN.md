# supervisor-rs — TECHNICAL_PLAN

Детальный технический план: стек, архитектура, разбивка по Этапам.
Терминология — «Этап N». Этап 0 — этот бутстрап.

## Стек

| Слой | Выбор | Обоснование |
|---|---|---|
| Язык | Rust (edition 2021, MSRV 1.85) | Первый Rust в портфеле; тема (сигналы, process groups, реапинг) требует низкоуровневого контроля над libc при memory-safety. |
| Syscalls | `nix` (features `signal`, `process`) | Безопасные обёртки над `kill`/`killpg`/`setsid`/`setpgid`/`waitpid`/`sigaction`. Идиоматичнее сырого `libc`. |
| Spawn | `std::process::Command` + `CommandExt::pre_exec` | Стандартный запуск; `pre_exec` даёт хук в дочернем процессе между fork и exec — там ставим process-группу. |
| Конфиг | `serde` + `toml` | Декларативный конфиг-файл со списком процессов и policy. |
| Логи | `tracing` + `tracing-subscriber` | Структурные логи; уровень через `RUST_LOG`. |
| Тесты | встроенный `cargo test` + `tempfile` (dev-dep) | Юнит-тесты на парсинг/policy; интеграционные — на реальных дочерних процессах-заглушках. |

### Docker Compose — НЕ нужен

Это CLI-демон без внешних сетевых зависимостей (нет БД, брокеров, HTTP-сервисов).
Запуск, тесты и отладка — целиком локальные (`cargo run` / `cargo test`).
Docker Compose в проекте **сознательно отсутствует** и добавлять его не следует.

## Модульная структура

```
src/
├── main.rs      # инициализация логов, разбор CLI, запуск supervise loop
├── lib.rs       # библиотечный крейт: реэкспорт модулей для бинарника и тестов
├── config.rs    # ProcessConfig, RestartPolicy, load() — парсинг TOML
├── clock.rs     # Clock / SystemClock / FakeClock — инъекция времени
├── supervise.rs # SupervisorLoop: monitor-loop, restart policy, backoff
└── process.rs   # spawn / teardown, process groups, waitpid
```

Логика намеренно разделена: `config` — чистый парсинг без сайд-эффектов (легко
юнит-тестировать), `process` — POSIX-механика запуска и (с Этапа 4) teardown,
`supervise` — оркестрация поверх них. Библиотечный крейт (`lib.rs`) появился в
Этапе 1, чтобы интеграционные тесты в `tests/` видели публичный API: тесты не
могут импортировать модули из бинарного крейта. `clock.rs` вынесен отдельно,
потому что от инъекции времени зависит детерминизм тестов backoff.

## Разбивка по Этапам

### Этап 0 — Bootstrap (готово)

- `cargo init`, `Cargo.toml` с зависимостями под будущий функционал.
- Модули-заглушки `config.rs`, `process.rs` с `// TODO(Этап N)`.
- `main.rs` инициализирует `tracing` и печатает баннер.
- Документация (`PLAN`, `TECHNICAL_PLAN`, `POST_MVP_PLAN`, `README`, `CLAUDE.md`).
- **Критерий приёмки:** `cargo check` и `cargo build` проходят чисто.

### Этап 1 — Конфиг-парсинг + базовый spawn (готово)

- В `config.rs`: `Config { process: Vec<ProcessConfig> }` и
  `ProcessConfig { name, command: Vec<String>, workdir: Option<PathBuf>,
  env: Option<BTreeMap<String,String>>, restart: RestartPolicy }` как
  `#[derive(Debug, Deserialize)]`.
- `load(path) -> Result<Config, ConfigError>`: чтение файла + `toml::from_str`,
  отдельный `ConfigError` (IO vs parse) через `thiserror`-стиль или ручной enum.
- В `process.rs`: `spawn(cfg) -> Result<Child, SpawnError>` через
  `std::process::Command` (workdir/env применяются), **без рестарта** — просто
  запустить все процессы из конфига и дождаться их (blocking `wait`).
- Пример конфига `examples/supervisor.toml`.
- **Тесты:** юнит на парсинг валидного/битого конфига; интеграционный — запуск
  короткоживущего процесса (`/bin/true`) и проверка кода выхода.
- **Критерий приёмки:** `supervisor-rs examples/supervisor.toml` (путь к
  конфигу — единственный позиционный аргумент, без подкоманды `run`; полноценные
  subcommands — Этап 5) стартует перечисленные процессы и завершается, когда они
  все вышли.

### Этап 2 — Restart policy + backoff (готово)

- `RestartPolicy { Always, OnFailure, Never }` с serde-rename в kebab-case
  (`config.rs`), дефолт — `on-failure`.
- Monitor-loop (`supervise.rs`, `SupervisorLoop<C: Clock>`): неблокирующий
  опрос всех детей + **реапинг зомби**; при выходе процесса — решение о
  рестарте по policy и коду выхода (`OnFailure` → рестарт только при
  ненулевом коде/сигнале).
  **Отклонение от изначального плана (осознанное):** опрос сделан через
  `std::process::Child::try_wait()`, а не через `waitpid(WNOHANG)` из `nix`.
  Причина — `Child` реапит своего потомка сам, и ручной `waitpid` по тому же
  pid дал бы двойной реапинг. В Этапе 4 решение уточнено: полного перехода на
  `waitpid` не было, вместо него гибрид «`waitid`-peek + `Child::try_wait`»
  (см. раздел Этапа 4).
- Экспоненциальный backoff между рестартами: initial 1s, factor 2, max 30s,
  сброс после 10s стабильной работы, чтобы crash-loop не молотил CPU.
  Ошибка повторного spawn тоже уходит в backoff, а не ретраится каждый тик.
- Стартовый spawn — best-effort: процесс, который не удалось запустить,
  логируется и пропускается, остальные супервизируются (аборт всего старта
  оставлял бы уже поднятых детей осиротевшими). Ошибки старта отражаются в
  exit-коде.
- **Тесты:** заглушка, падающая с заданным кодом; проверка, что `never` не
  рестартит, `always` рестартит всегда, `on-failure` — только при провале;
  проверка нарастания задержки backoff — через инъекцию «часов»
  (`clock.rs`: `Clock` / `SystemClock` / `FakeClock`), без реальных sleep.
- **Критерий приёмки:** падающий процесс с `on-failure` перезапускается с
  растущей задержкой; с `never` — нет.

### Этап 3 — Форвардинг сигналов (готово)

- Установка обработчиков SIGTERM/SIGINT у супервизора (`signal.rs`,
  `install_handlers()`) — до первого spawn'а: сигнал, пришедший в окно между
  стартом ребёнка и установкой хендлера, убил бы супервизор по `SIG_DFL` и
  осиротил уже запущенных детей.
  Диспозиция **никогда не `SIG_IGN`**: «игнорировать» наследуется через `exec` и
  сделала бы всех детей глухими к SIGTERM, тогда как настоящий хендлер при `exec`
  сбрасывается в `SIG_DFL` — это и нужно.
- Полученный сигнал форвардится дочернему процессу
  (`process::forward_signal` → `kill(child_pid, sig)`; функция удалена в Этапе 4,
  её заменил `signal_group`). `ESRCH` — успех: ребёнок
  уже умер, но ещё не реапнут. Звать только для НЕ реапнутого `Child` — после
  реапинга ОС может переиспользовать pid.

  **Отклонение от изначального плана (осознанное): вместо self-pipe/signalfd —
  глобальный `static PENDING: AtomicI32`.** Хендлер делает ровно одну атомарную
  запись, `run()` опрашивает флаг через `take_pending()` на каждой итерации.
  Причина: self-pipe существует, чтобы *разбудить* цикл, блокирующийся на
  дескрипторе (`select`/`poll`/`read`), а `run()` — poll-loop с
  `tick()` + `clock.sleep(50ms)`, будить нечего; достаточно, чтобы следующая
  итерация увидела флаг. Атомарная запись — единственное, что POSIX прямо
  разрешает в хендлере, и она проще: нет fd, нет `O_NONBLOCK`, нет EINTR-ретраев,
  нет утечки дескрипторов в детей (pipe пришлось бы помечать `FD_CLOEXEC`).
  Цена — латентность до одного тика (50 мс).
  **Условие пересмотра:** если цикл станет событийным (например, unix-socket с
  `poll` в Этапе 5) — вернуться к self-pipe/signalfd.
- **Режим shutdown** (`SupervisorLoop::begin_shutdown`) подавляет рестарты.
  Без этого форварднутый SIGTERM убил бы ребёнка, `tick()` увидел бы выход и по
  policy `always`/`on-failure` перезапустил его — супервизор не завершился бы
  никогда. Флаг — поле `SupervisorLoop`, а не глобаль, чтобы тесты могли звать
  `begin_shutdown()` без реальных сигналов. Опрос сигнала живёт в `run()`, а не в
  `tick()`: `tick()` остаётся свободным от процессно-глобального состояния, его
  дёргают напрямую интеграционные тесты.
  Живому ребёнку `done` при этом НЕ выставляется — только при реапинге в
  `tick()`, иначе цикл вышел бы, оставив ребёнка сиротой.
- **Exit-код при штатном shutdown по сигналу — `0`.** Приоритет: неверные
  аргументы → 2; ошибка конфига → 1; `had_start_errors` → 1; иначе 0. Остановка
  демона сигналом — штатный сценарий (как у systemd-юнита), а не отказ.
  Отвергнутая альтернатива — шелл-конвенция `128+signo` (143/130): она означает
  «процесс *убит* сигналом», что честно выражается только реальной смертью от
  сигнала (re-raise), а re-raise конфликтует с приоритетом `had_start_errors`.
- **Ограничение Этапа 3, снято в Этапе 4:** эскалации до SIGKILL не было,
  поэтому ребёнок, игнорирующий SIGTERM, подвешивал супервизор навсегда, а
  второй сигнал только логировался. Теперь есть дедлайн `stop-grace-secs` и
  немедленная эскалация по второму сигналу. Снят именно случай «игнорирует
  SIGTERM»; процесс, который не умирает **и от SIGKILL** (uninterruptible sleep
  в D-state на залипшем NFS/FUSE, трассируемый процесс), по-прежнему держит
  супервизор бесконечно — верхней границы на весь shutdown нет, в отличие от
  systemd. См. «Известные ограничения Этапа 4». Чтобы регрессия давала красный тест, а не
  зависший CI, интеграционные тесты ждут супервизор через `wait_with_timeout` с
  дедлайном 5 с (по таймауту — SIGKILL супервизору и `panic!`).
- **Ловушка ручной проверки (снята в Этапе 4):** Ctrl-C в терминале доставлял
  SIGINT всей foreground-группе процессов, то есть и детям напрямую — пока у них
  не было своей process-группы. Поэтому «проверил руками в шелле, дети умерли»
  ничего не доказывало: форвардинг мог быть сломан. Тесты (`tests/signals.rs`)
  шлют адресный `kill(supervisor_pid)` именно поэтому. После `setsid` в Этапе 4
  терминальные сигналы до детей не доходят вообще, и ручной Ctrl-C стал честной
  проверкой.
- **Техдолг Этапа 3 — закрыт в Этапе 4:** ошибка опроса в `tick()`
  (`supervise.rs`) логировалась, но процесс оставался `child = Some(...)`,
  `done = false` — `run()` крутился вечно на 20 итерациях/с, заливая лог.
  Починено счётчиком подряд идущих ошибок: см. раздел Этапа 4.
- **Тесты:** `tests/signals.rs` — на реальном бинарнике: заглушка на `sh` с
  трапами на TERM/INT пишет маркер-файл, супервизору шлётся сигнал, проверяется
  маркер, отсутствие сиротства (`kill(pid, 0)` → `ESRCH`), exit-код 0 и то, что
  policy `always` не воскрешает заглушку во время shutdown. Трапы взводятся ДО
  записи pid-файла, поэтому появление pid-файла = «ловушка взведена» — тест
  поллит его, прежде чем слать сигнал. `tests/shutdown.rs` — in-process,
  с `FakeClock` и без установки реальных хендлеров (`sigaction`
  процессно-глобальна, а `cargo test` гоняет тесты в потоках одного процесса).
- **Критерий приёмки:** SIGTERM супервизору приводит к SIGTERM у ребёнка, а не к
  сиротству ребёнка. ✅

### Этап 4 — Process groups + деревья процессов (ядро проекта, готово)

- При spawn — `Command::pre_exec(|| setsid())` (`process.rs`): каждый
  супервизируемый процесс становится лидером собственной сессии и process-группы.
  Выбран `setsid`, а не `setpgid(0, 0)`: в этой позиции он не может отказать
  (свежеформленный ребёнок никогда не лидер группы — единственное условие ошибки),
  и он же отвязывает ребёнка от управляющего терминала, чем снимает ловушку
  ручной проверки Этапа 3. Цена — у детей нет управляющего терминала; для
  супервизируемых демонов это норма (так делает и systemd).
- Форвардинг Этапа 3 переведён с `kill(pid)` на `killpg(pgid)`:
  `process::forward_signal` удалён, введён `process::signal_group(pgid, sig)`.
  `ESRCH` по-прежнему трактуется как успех.
- **Центральный инвариант: зомби-лидер пиннит pgid.** Пока лидер группы не
  реапнут, он существует как зомби, а pgid существующей группы ядро
  переиспользовать не может. Отсюда обязательный порядок в каждой точке, где
  лидер вышел: **peek → killpg-sweep → reap**. Реапнуть до sweep — открыть
  TOCTOU-окно, в котором ОС отдаёт pgid новой группе и SIGKILL уходит по
  невиновным. `Supervised.pgid: Option<Pid>` — структурная запись этого
  инварианта: `Some` = «killpg по этому id безопасен», `None` = «группа больше
  не наша».

**Три осознанных отклонения от изначального плана этого раздела:**

1. **Реапинг — гибрид `waitid`-peek + `Child::try_wait`, а не полный переход на
   `nix::waitpid` (решение принято пользователем).** Владельцем pid остаётся
   `std::process::Child` — реапит только он, двойного реапинга нет по построению;
   обнаружение выхода — неразрушающий peek `waitid(P_PID, pid, WEXITED | WNOHANG
   | WNOWAIT)` (`process::peek_exited`), который сообщает статус, **не реапя**
   процесс, — именно это и позволяет держать порядок peek → sweep → reap.
   Полный переход на `waitpid` не дал бы ничего: `waitpid` реапит только прямых
   детей, а внуки при смерти лидера переходят к `init`/subreaper, и супервизор их
   реапить не может в принципе. Гибрид берёт от `nix` ровно то, чего нет у `std`:
   неразрушающий peek и `killpg`.
   **Грабля:** `WNOWAIT` валиден только для `waitid(2)`; `waitpid(2)`/`wait4(2)`
   отвечают `EINVAL` (проверено эмпирически на Linux 6.8).
2. **Машина состояний в `tick()` вместо блокирующей `terminate_tree(pgid,
   grace)`.** Блокирующий grace сериализуется по процессам (N × grace на
   shutdown из N процессов), не наблюдаем извне и не проверяется `FakeClock`.
   Вместо него — состояние на процесс (`StopPhase::{Idle, Terminating{deadline},
   Killing}`), продвигаемое обычным `tick()` по инъектируемым часам: все группы
   гасятся параллельно, обе стороны дедлайна тестируются без реальных секунд.
   `begin_shutdown` шлёт сигнал группам и взводит дедлайны; второй сигнал зовёт
   `escalate_to_kill()` — немедленный SIGKILL всем группам без остатка grace.
3. **Выход лидера ⇒ немедленный SIGKILL-sweep остатка группы** — и в shutdown, и
   на обычном пути рестарта. Grace защищает завершение *лидера*; после его смерти
   оставшиеся члены группы — отставшие сироты, ждать их нечем: без cgroups нет
   race-free способа дождаться опустения группы (зомби-лидер делает
   `killpg(pgid, 0)` вечно-успешным, а реапнуть лидера до sweep запрещает
   инвариант). Лидер, желающий мягкой остановки своих детей, обязан сам дождаться
   их перед выходом — стандартная практика. На пути рестарта это же и гарантирует,
   что новый инстанс не поднимется поверх старого дерева.

- **Новое поле конфига `stop-grace-secs`** (решение принято пользователем):
  целые секунды между сигналом группе и эскалацией до SIGKILL, дефолт 5
  (`DEFAULT_STOP_GRACE_SECS`). Kebab-имя — в стиле значений `restart`.
  Целые секунды по замыслу: TOML-integer не требует парсера длительностей, а
  отрицательные значения отсекает сам тип `u64`.
- **Техдолг Этапа 3 закрыт:** подряд идущие ошибки опроса считаются
  (`MAX_CONSECUTIVE_POLL_ERRORS = 20`, ~1 с при тике 50 мс); по исчерпании —
  best-effort `killpg(SIGKILL)`, финальная попытка реапа, `done = true` и лог
  уровня `error`. Счётчик сбрасывается при любом успешном опросе. Exit-код
  супервизора не трогается: сдача отражается только в логе.
- **Тесты.** `tests/tree.rs` (реальный бинарник): `shutdown_kills_whole_tree` —
  заглушка форкает двух долгоживущих внуков, **глухих к SIGTERM** (иначе тест был
  бы зелёным и при полностью отсутствующем sweep — он доказывал бы только
  групповой форвардинг), после SIGTERM супервизору все три pid-а обязаны исчезнуть;
  `sigkill_escalation_when_child_ignores_sigterm` — путь SIGKILL по дедлайну
  (`stop-grace-secs = 1`); `second_signal_escalates_immediately` — второй сигнал
  при grace 30 с, handshake через поллинг лога, а не sleep. `tests/shutdown.rs`
  (in-process, `FakeClock`): `escalation_waits_for_grace_deadline` (обе стороны
  дедлайна), `escalate_to_kill_skips_grace`, `leader_exit_sweeps_leftover_grandchildren`
  (тердаун на пути рестарта). Юниты: `spawned_child_leads_own_process_group`,
  `peek_exited_does_not_reap`, `poll_error_budget_exhausts_after_max`, парсинг
  `stop-grace-secs`.
  **Смерть внука наблюдается только поллингом с дедлайном:** прямого ребёнка
  реапит сам супервизор, а внука — init, асинхронно, и до этого момента он зомби,
  по которому `kill(pid, 0)` возвращает успех. Одиночный `assert` на `ESRCH`
  сразу после выхода супервизора — гарантированный флейк.
- **Критерий приёмки:** завершение супервизора не оставляет ни одного потомка
  дерева живым; зомби не накапливаются. ✅ — на всех штатных путях; единственное
  исключение перечислено ниже.

#### Известные ограничения Этапа 4

Перечислены явно, чтобы следующий проход не принял их за недоделку и не начал
«чинить» осознанные решения.

1. **Нет верхней границы на shutdown целиком.** Процесс, переживающий SIGKILL
   (D-state), оставляет супервизор в фазе `Killing` навсегда. Ошибку доставки
   SIGKILL мы ретраим раз в секунду (`KILL_RETRY`), но против D-state ретрай
   бессилен — там сигнал доставлен и просто не может быть обработан.
   Интеграционные тесты защищены `wait_with_timeout`, поэтому в CI это даёт
   красное, а не зависание. Финальный таймаут — кандидат в Этап 5+.
2. **Путь сдачи по бюджету ошибок опроса может оставить зомби или сироту.**
   Исчерпав `MAX_CONSECUTIVE_POLL_ERRORS`, супервизор бьёт группу SIGKILL-ом,
   пробует дореапить лидера (10 попыток по 10 мс) и отпускает `Child`. Если
   реапинг не успел — остаётся зомби до выхода супервизора; если сам SIGKILL
   отказал — остаётся живая сирота. Оба исхода пишутся в лог явным
   `error`-сообщением, а не проглатываются. Ветка требует аномального errno от
   `waitid` (`SA_RESTART` исключает EINTR), поэтому дальше не укрепляем.
3. **`stop-grace-secs` не достаётся внукам, если лидер вышел раньше срока.**
   Прямое следствие правила «выход лидера ⇒ немедленный sweep» (обоснование
   выше). Практическая ловушка: `["/bin/sh", "-c", "myapp"]` без `exec` делает
   лидером шелл, тот умирает на SIGTERM мгновенно, и `myapp` добивается
   SIGKILL-ом через миллисекунды. Задокументировано в
   `examples/supervisor.toml`.
4. **Инвариант «зомби-лидер пиннит pgid» держится, пока лидер остаётся в своей
   группе.** Супервизируемый процесс, сам зовущий `setsid`/`setpgid` (классический
   демон с двойным форком), уходит из группы и из-под контроля супервизора.
   Без cgroups это принципиально нерешаемо; `Some(pgid)` — гарантия при
   добросовестном ребёнке, а не абсолютная.
5. **Ветка сдачи по бюджету ошибок не покрыта e2e-тестом.** Покрыта юнитом на
   `record_poll_error` и тестом, дёргающим `handle_poll_error` напрямую;
   инъекция errno в `waitid` мока не стоит.

#### Техдолг, найден на ревью Этапа 4

В отличие от списка выше (там — принятое поведение), это отложенные правки.
У каждой указан триггер пересмотра, чтобы решение «потом» не превратилось в
«никогда» и не всплыло заново как «находка».

- **`child` и `pgid` — два `Option`, обязанных быть согласованными**
  (`supervise.rs`, структура `Supervised`). Инвариант
  `child.is_some() ⟺ pgid.is_some()` держится во всех точках мутации, но не
  выражен типом, из-за чего `if let Some(pgid)` внутри `if let Some(child)` —
  фактически мёртвые ветки. Просится `running: Option<Running { child, pgid }>`.
  Не сделано: правка структурная, а этап уже был закрыт и зелёный.
  **Триггер:** Этап 5 добавляет в `Supervised` поля для `status` (uptime,
  состояние). Как только появится третье поле, живущее ровно на время жизни
  ребёнка, — объединять, дальше тянуть дороже.
- **Параллельность гашения не проверена ни одним тестом.** Это главный аргумент
  против блокирующей `terminate_tree` (N × grace), но конфига с **разными**
  `stop-grace-secs` у разных процессов в тестах нет: все тесты гасят один
  процесс. **Триггер:** любая правка `begin_shutdown`/`tick()`, трогающая
  дедлайны, — сначала добавить такой тест, иначе регрессия «дедлайн стал общим»
  пройдёт незамеченной.
- **Рестарт после sweep не проверяет новый pgid.**
  `leader_exit_sweeps_leftover_grandchildren` останавливается на «рестарт
  запланирован»; что новый инстанс поднялся и получил **свою** группу — не
  проверено. **Триггер:** при любой правке ветки респавна в `tick()`.
- **Три копии `wait_for_pid` в `tests/` с разошедшейся семантикой**
  (`signals.rs`, `shutdown.rs` — ждут одну строку; `tree.rs::wait_for_pids` —
  парсит все и закрывает окно open/write). Дублирование между интеграционными
  крейтами осознанное, но расхождение контрактов — заявка на то, что следующая
  правка попадёт в одну из трёх. **Триггер:** появление четвёртой копии.
- **`wait_until_gone` считает `EPERM` за «жив»** и уязвим к переиспользованию
  pid в окне поллинга. Чинить нечем — это фундаментальное ограничение проверки
  по pid; ошибка даёт **красное, а не зелёное**, то есть флейк, а не потерю
  покрытия. Записано, чтобы при разборе будущего флейка не искать баг в
  супервизоре.

### Этап 5 — CLI статуса/управления

- Подкоманды: `run <config>` (демон, уже есть), `status` (список процессов и их
  состояние: running/restarting/stopped, PID, restart-count, uptime).
- Обмен состоянием — через простой локальный канал: файл состояния или Unix-domain
  socket (решение принять в начале Этапа 5; для v1 достаточно файла состояния,
  который демон периодически пишет, а `status` читает).
- Ручной разбор `std::env::args` или лёгкий клап-аналог; тяжёлый CLI-фреймворк
  для 2–3 подкоманд избыточен — решить на месте.
- **Тесты:** `status` на запущенном демоне печатает ожидаемые строки; на
  незапущенном — внятную ошибку.
- **Критерий приёмки:** `supervisor-rs status` показывает актуальное состояние
  супервизируемых процессов.

#### На входе в Этап 5 — что тянется из предыдущих этапов

Открытый выбор «файл состояния против unix-socket» не изолирован: он тянет за
собой два решения, принятых раньше. Проверить до начала кодинга, а не после.

1. **Unix-socket с `poll` включает условие пересмотра из Этапа 3.** Механизм
   перехвата сигналов (`signal.rs`, глобальный `AtomicI32` + опрос в `run()`)
   выбран именно потому, что цикл — поллинговый и будить нечего. Событийный
   цикл это условие ломает: понадобится self-pipe или `signalfd`, чтобы сигнал
   разбудил `poll`. Формулировка условия — в разделе Этапа 3. **Файл состояния
   этого не требует** — ещё один довод за него для v1.
2. **Подкоманды ломают текущий контракт CLI.** Сейчас единственный позиционный
   аргумент — путь к конфигу (`main.rs`), и это зафиксировано тестами
   `tests/cli.rs` и критерием приёмки Этапа 1. Переход на `run <config>` —
   несовместимое изменение: обновить оба места и явно решить, оставлять ли
   старую форму как алиас.
3. **Состояние для `status` живёт в `Supervised`** (`supervise.rs`), который уже
   несёт `child`/`pgid`/`stop`/`poll_errors`. Добавление полей под uptime и
   состояние — тот самый триггер из техдолга Этапа 4 (объединить `child` и
   `pgid` в один `Option<Running>`); сделать это до добавления новых полей, а не
   после.
