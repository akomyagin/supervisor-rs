# supervisor-rs — TECHNICAL_PLAN

Детальный технический план: стек, архитектура, разбивка по Этапам.
Терминология — «Этап N». Этап 0 — этот бутстрап.

## Стек

| Слой | Выбор | Обоснование |
|---|---|---|
| Язык | Rust (edition 2021, MSRV 1.85) | Первый Rust в портфеле; тема (сигналы, process groups, реапинг) требует низкоуровневого контроля над libc при memory-safety. |
| Syscalls | `nix` (features `signal`, `process`) | Безопасные обёртки над `kill`/`killpg`/`setsid`/`setpgid`/`waitpid`/`sigaction`. Идиоматичнее сырого `libc`. |
| Spawn | `std::process::Command` + `CommandExt::pre_exec` | Стандартный запуск; `pre_exec` даёт хук в дочернем процессе между fork и exec — там ставим process-группу. |
| Конфиг | `serde` + `toml` | Декларативный конфиг-файл со списком процессов и policy. |
| Логи | `tracing` + `tracing-subscriber` | Структурные логи; уровень через `RUST_LOG`. |
| Тесты | встроенный `cargo test` + `tempfile` (dev-dep) | Юнит-тесты на парсинг/policy; интеграционные — на реальных дочерних процессах-заглушках. |

### Docker Compose — НЕ нужен

Это CLI-демон без внешних сетевых зависимостей (нет БД, брокеров, HTTP-сервисов).
Запуск, тесты и отладка — целиком локальные (`cargo run` / `cargo test`).
Docker Compose в проекте **сознательно отсутствует** и добавлять его не следует.

## Модульная структура

```
src/
├── main.rs      # инициализация логов, диспетчер подкоманд, вывод status
├── lib.rs       # библиотечный крейт: реэкспорт модулей для бинарника и тестов
├── cli.rs       # Command / parse() / usage() — ручной разбор argv (Этап 5, расширен в Этапе 6)
├── config.rs    # ProcessConfig, RestartPolicy, load() — парсинг TOML
├── clock.rs     # Clock / SystemClock / FakeClock — инъекция времени
├── state.rs     # StateSnapshot, атомарная запись/чтение файла состояния (Этап 5)
├── signal.rs    # обработчики SIGTERM/SIGINT (Этап 3) + SIGHUP/reload (Этап 8)
├── control.rs   # control-socket: протокол, ControlServer, клиент (Этап 6)
├── health.rs    # exec/tcp/http пробы: run_probe(), ProbeError (Этап 7)
├── logs.rs      # RotatingFile + поток-читатель pipe: захват stdout/stderr, ротация по размеру (Этап 9)
├── supervise.rs # SupervisorLoop: monitor-loop, restart policy, backoff, снапшот, handle_command
└── process.rs   # spawn / teardown, process groups, waitpid
```

Логика намеренно разделена: `config` — чистый парсинг без сайд-эффектов (легко
юнит-тестировать), `process` — POSIX-механика запуска и (с Этапа 4) teardown,
`supervise` — оркестрация поверх них. Библиотечный крейт (`lib.rs`) появился в
Этапе 1, чтобы интеграционные тесты в `tests/` видели публичный API: тесты не
могут импортировать модули из бинарного крейта. `clock.rs` вынесен отдельно,
потому что от инъекции времени зависит детерминизм тестов backoff. `cli.rs` и
`state.rs` добавлены в Этапе 5 и живут в библиотеке по той же причине: разбор
аргументов и формат снапшота — чистые функции, которые надо уметь звать из
тестов, а `main.rs` остаётся тонкой обвязкой IO и exit-кодов. `control.rs`
добавлен в Этапе 6 по тому же принципу: протокол и `ControlServer` — код,
который юнит-тестируется без всякого запуска демона. `health.rs` добавлен в
Этапе 7 и намеренно не знает ни о `SupervisorLoop`, ни о `Clock`: это чистая
функция «выполни одну пробу за ограниченное реальное время», юнит-тестируемая
на реальных сокетах и командах — расписание же (когда проба должна случиться)
живёт в `supervise.rs` и ездит на инъектируемых часах. `logs.rs` добавлен в
Этапе 9 по тому же принципу и так же ничего не знает о `SupervisorLoop` и
`Clock`: чистое ядро ротации (`RotatingFile`, юнит-тестируемое на tempdir без
процессов и потоков) плюс функция запуска потока-читателя pipe. Часов у него нет
вообще — ротация есть функция размера, не времени.

## Разбивка по Этапам

### Этап 0 — Bootstrap (готово)

- `cargo init`, `Cargo.toml` с зависимостями под будущий функционал.
- Модули-заглушки `config.rs`, `process.rs` с `// TODO(Этап N)`.
- `main.rs` инициализирует `tracing` и печатает баннер.
- Документация (`PLAN`, `TECHNICAL_PLAN`, `POST_MVP_PLAN`, `README`, `CLAUDE.md`).
- **Критерий приёмки:** `cargo check` и `cargo build` проходят чисто.

### Этап 1 — Конфиг-парсинг + базовый spawn (готово)

- В `config.rs`: `Config { process: Vec<ProcessConfig> }` и
  `ProcessConfig { name, command: Vec<String>, workdir: Option<PathBuf>,
  env: Option<BTreeMap<String,String>>, restart: RestartPolicy }` как
  `#[derive(Debug, Deserialize)]`.
- `load(path) -> Result<Config, ConfigError>`: чтение файла + `toml::from_str`,
  отдельный `ConfigError` (IO vs parse) через `thiserror`-стиль или ручной enum.
- В `process.rs`: `spawn(cfg) -> Result<Child, SpawnError>` через
  `std::process::Command` (workdir/env применяются), **без рестарта** — просто
  запустить все процессы из конфига и дождаться их (blocking `wait`).
- Пример конфига `examples/supervisor.toml`.
- **Тесты:** юнит на парсинг валидного/битого конфига; интеграционный — запуск
  короткоживущего процесса (`/bin/true`) и проверка кода выхода.
- **Критерий приёмки (форма изменена в Этапе 5):** супервизор стартует
  перечисленные в конфиге процессы и завершается, когда они все вышли.
  До Этапа 5 запуск выглядел как `supervisor-rs examples/supervisor.toml` —
  путь к конфигу был единственным позиционным аргументом. Этап 5 по решению
  пользователя заменил эту форму подкомандой:
  `supervisor-rs run examples/supervisor.toml`, **без обратно-совместимого
  алиаса** — старая форма теперь usage-ошибка (exit 2), что зафиксировано
  тестами `cli::tests::rejects_bare_config_path_without_subcommand` и
  `tests/cli.rs::bare_config_path_is_a_usage_error`.

### Этап 2 — Restart policy + backoff (готово)

- `RestartPolicy { Always, OnFailure, Never }` с serde-rename в kebab-case
  (`config.rs`), дефолт — `on-failure`.
- Monitor-loop (`supervise.rs`, `SupervisorLoop<C: Clock>`): неблокирующий
  опрос всех детей + **реапинг зомби**; при выходе процесса — решение о
  рестарте по policy и коду выхода (`OnFailure` → рестарт только при
  ненулевом коде/сигнале).
  **Отклонение от изначального плана (осознанное):** опрос сделан через
  `std::process::Child::try_wait()`, а не через `waitpid(WNOHANG)` из `nix`.
  Причина — `Child` реапит своего потомка сам, и ручной `waitpid` по тому же
  pid дал бы двойной реапинг. В Этапе 4 решение уточнено: полного перехода на
  `waitpid` не было, вместо него гибрид «`waitid`-peek + `Child::try_wait`»
  (см. раздел Этапа 4).
- Экспоненциальный backoff между рестартами: initial 1s, factor 2, max 30s,
  сброс после 10s стабильной работы, чтобы crash-loop не молотил CPU.
  Ошибка повторного spawn тоже уходит в backoff, а не ретраится каждый тик.
- Стартовый spawn — best-effort: процесс, который не удалось запустить,
  логируется и пропускается, остальные супервизируются (аборт всего старта
  оставлял бы уже поднятых детей осиротевшими). Ошибки старта отражаются в
  exit-коде.
- **Тесты:** заглушка, падающая с заданным кодом; проверка, что `never` не
  рестартит, `always` рестартит всегда, `on-failure` — только при провале;
  проверка нарастания задержки backoff — через инъекцию «часов»
  (`clock.rs`: `Clock` / `SystemClock` / `FakeClock`), без реальных sleep.
- **Критерий приёмки:** падающий процесс с `on-failure` перезапускается с
  растущей задержкой; с `never` — нет.

### Этап 3 — Форвардинг сигналов (готово)

- Установка обработчиков SIGTERM/SIGINT у супервизора (`signal.rs`,
  `install_handlers()`) — до первого spawn'а: сигнал, пришедший в окно между
  стартом ребёнка и установкой хендлера, убил бы супервизор по `SIG_DFL` и
  осиротил уже запущенных детей.
  Диспозиция **никогда не `SIG_IGN`**: «игнорировать» наследуется через `exec` и
  сделала бы всех детей глухими к SIGTERM, тогда как настоящий хендлер при `exec`
  сбрасывается в `SIG_DFL` — это и нужно.
- Полученный сигнал форвардится дочернему процессу
  (`process::forward_signal` → `kill(child_pid, sig)`; функция удалена в Этапе 4,
  её заменил `signal_group`). `ESRCH` — успех: ребёнок
  уже умер, но ещё не реапнут. Звать только для НЕ реапнутого `Child` — после
  реапинга ОС может переиспользовать pid.

  **Отклонение от изначального плана (осознанное): вместо self-pipe/signalfd —
  глобальный `static PENDING: AtomicI32`.** Хендлер делает ровно одну атомарную
  запись, `run()` опрашивает флаг через `take_pending()` на каждой итерации.
  Причина: self-pipe существует, чтобы *разбудить* цикл, блокирующийся на
  дескрипторе (`select`/`poll`/`read`), а `run()` — poll-loop с
  `tick()` + `clock.sleep(50ms)`, будить нечего; достаточно, чтобы следующая
  итерация увидела флаг. Атомарная запись — единственное, что POSIX прямо
  разрешает в хендлере, и она проще: нет fd, нет `O_NONBLOCK`, нет EINTR-ретраев,
  нет утечки дескрипторов в детей (pipe пришлось бы помечать `FD_CLOEXEC`).
  Цена — латентность до одного тика (50 мс).
  **Условие пересмотра:** если цикл станет событийным (например, unix-socket с
  `poll`) — вернуться к self-pipe/signalfd. **В Этапе 5 условие не сработало:**
  каналом для `status` выбран файл состояния, цикл остался поллинговым, и
  `signal.rs` не менялся. **В Этапе 6 условие не сработало снова:** control-socket
  появился, но по решению пользователя он встроен в тот же поллинговый цикл
  (неблокирующий `accept` раз в тик), а не переводит его на событийную модель —
  подробности в разделе Этапа 6. Прежнее ожидание «событийный цикл наступит
  вместе с control-socket из POST-MVP» не подтвердилось.
- **Режим shutdown** (`SupervisorLoop::begin_shutdown`) подавляет рестарты.
  Без этого форварднутый SIGTERM убил бы ребёнка, `tick()` увидел бы выход и по
  policy `always`/`on-failure` перезапустил его — супервизор не завершился бы
  никогда. Флаг — поле `SupervisorLoop`, а не глобаль, чтобы тесты могли звать
  `begin_shutdown()` без реальных сигналов. Опрос сигнала живёт в `run()`, а не в
  `tick()`: `tick()` остаётся свободным от процессно-глобального состояния, его
  дёргают напрямую интеграционные тесты.
  Живому ребёнку `done` при этом НЕ выставляется — только при реапинге в
  `tick()`, иначе цикл вышел бы, оставив ребёнка сиротой.
- **Exit-код при штатном shutdown по сигналу — `0`.** Приоритет: неверные
  аргументы → 2; ошибка конфига → 1; `had_start_errors` → 1; иначе 0. Остановка
  демона сигналом — штатный сценарий (как у systemd-юнита), а не отказ.
  Отвергнутая альтернатива — шелл-конвенция `128+signo` (143/130): она означает
  «процесс *убит* сигналом», что честно выражается только реальной смертью от
  сигнала (re-raise), а re-raise конфликтует с приоритетом `had_start_errors`.
- **Ограничение Этапа 3, снято в Этапе 4:** эскалации до SIGKILL не было,
  поэтому ребёнок, игнорирующий SIGTERM, подвешивал супервизор навсегда, а
  второй сигнал только логировался. Теперь есть дедлайн `stop-grace-secs` и
  немедленная эскалация по второму сигналу. Снят именно случай «игнорирует
  SIGTERM»; процесс, который не умирает **и от SIGKILL** (uninterruptible sleep
  в D-state на залипшем NFS/FUSE, трассируемый процесс), по-прежнему держит
  супервизор бесконечно — верхней границы на весь shutdown нет, в отличие от
  systemd. См. «Известные ограничения Этапа 4». Чтобы регрессия давала красный тест, а не
  зависший CI, интеграционные тесты ждут супервизор через `wait_with_timeout` с
  дедлайном 5 с (по таймауту — SIGKILL супервизору и `panic!`).
- **Ловушка ручной проверки (снята в Этапе 4):** Ctrl-C в терминале доставлял
  SIGINT всей foreground-группе процессов, то есть и детям напрямую — пока у них
  не было своей process-группы. Поэтому «проверил руками в шелле, дети умерли»
  ничего не доказывало: форвардинг мог быть сломан. Тесты (`tests/signals.rs`)
  шлют адресный `kill(supervisor_pid)` именно поэтому. После `setsid` в Этапе 4
  терминальные сигналы до детей не доходят вообще, и ручной Ctrl-C стал честной
  проверкой.
- **Техдолг Этапа 3 — закрыт в Этапе 4:** ошибка опроса в `tick()`
  (`supervise.rs`) логировалась, но процесс оставался `child = Some(...)`,
  `done = false` — `run()` крутился вечно на 20 итерациях/с, заливая лог.
  Починено счётчиком подряд идущих ошибок: см. раздел Этапа 4.
- **Тесты:** `tests/signals.rs` — на реальном бинарнике: заглушка на `sh` с
  трапами на TERM/INT пишет маркер-файл, супервизору шлётся сигнал, проверяется
  маркер, отсутствие сиротства (`kill(pid, 0)` → `ESRCH`), exit-код 0 и то, что
  policy `always` не воскрешает заглушку во время shutdown. Трапы взводятся ДО
  записи pid-файла, поэтому появление pid-файла = «ловушка взведена» — тест
  поллит его, прежде чем слать сигнал. `tests/shutdown.rs` — in-process,
  с `FakeClock` и без установки реальных хендлеров (`sigaction`
  процессно-глобальна, а `cargo test` гоняет тесты в потоках одного процесса).
- **Критерий приёмки:** SIGTERM супервизору приводит к SIGTERM у ребёнка, а не к
  сиротству ребёнка. ✅

### Этап 4 — Process groups + деревья процессов (ядро проекта, готово)

- При spawn — `Command::pre_exec(|| setsid())` (`process.rs`): каждый
  супервизируемый процесс становится лидером собственной сессии и process-группы.
  Выбран `setsid`, а не `setpgid(0, 0)`: в этой позиции он не может отказать
  (свежеформленный ребёнок никогда не лидер группы — единственное условие ошибки),
  и он же отвязывает ребёнка от управляющего терминала, чем снимает ловушку
  ручной проверки Этапа 3. Цена — у детей нет управляющего терминала; для
  супервизируемых демонов это норма (так делает и systemd).
- Форвардинг Этапа 3 переведён с `kill(pid)` на `killpg(pgid)`:
  `process::forward_signal` удалён, введён `process::signal_group(pgid, sig)`.
  `ESRCH` по-прежнему трактуется как успех.
- **Центральный инвариант: зомби-лидер пиннит pgid.** Пока лидер группы не
  реапнут, он существует как зомби, а pgid существующей группы ядро
  переиспользовать не может. Отсюда обязательный порядок в каждой точке, где
  лидер вышел: **peek → killpg-sweep → reap**. Реапнуть до sweep — открыть
  TOCTOU-окно, в котором ОС отдаёт pgid новой группе и SIGKILL уходит по
  невиновным. `Supervised.pgid: Option<Pid>` — структурная запись этого
  инварианта: `Some` = «killpg по этому id безопасен», `None` = «группа больше
  не наша».

**Три осознанных отклонения от изначального плана этого раздела:**

1. **Реапинг — гибрид `waitid`-peek + `Child::try_wait`, а не полный переход на
   `nix::waitpid` (решение принято пользователем).** Владельцем pid остаётся
   `std::process::Child` — реапит только он, двойного реапинга нет по построению;
   обнаружение выхода — неразрушающий peek `waitid(P_PID, pid, WEXITED | WNOHANG
   | WNOWAIT)` (`process::peek_exited`), который сообщает статус, **не реапя**
   процесс, — именно это и позволяет держать порядок peek → sweep → reap.
   Полный переход на `waitpid` не дал бы ничего: `waitpid` реапит только прямых
   детей, а внуки при смерти лидера переходят к `init`/subreaper, и супервизор их
   реапить не может в принципе. Гибрид берёт от `nix` ровно то, чего нет у `std`:
   неразрушающий peek и `killpg`.
   **Грабля:** `WNOWAIT` валиден только для `waitid(2)`; `waitpid(2)`/`wait4(2)`
   отвечают `EINVAL` (проверено эмпирически на Linux 6.8).
2. **Машина состояний в `tick()` вместо блокирующей `terminate_tree(pgid,
   grace)`.** Блокирующий grace сериализуется по процессам (N × grace на
   shutdown из N процессов), не наблюдаем извне и не проверяется `FakeClock`.
   Вместо него — состояние на процесс (`StopPhase::{Idle, Terminating{deadline},
   Killing}`), продвигаемое обычным `tick()` по инъектируемым часам: все группы
   гасятся параллельно, обе стороны дедлайна тестируются без реальных секунд.
   `begin_shutdown` шлёт сигнал группам и взводит дедлайны; второй сигнал зовёт
   `escalate_to_kill()` — немедленный SIGKILL всем группам без остатка grace.
3. **Выход лидера ⇒ немедленный SIGKILL-sweep остатка группы** — и в shutdown, и
   на обычном пути рестарта. Grace защищает завершение *лидера*; после его смерти
   оставшиеся члены группы — отставшие сироты, ждать их нечем: без cgroups нет
   race-free способа дождаться опустения группы (зомби-лидер делает
   `killpg(pgid, 0)` вечно-успешным, а реапнуть лидера до sweep запрещает
   инвариант). Лидер, желающий мягкой остановки своих детей, обязан сам дождаться
   их перед выходом — стандартная практика. На пути рестарта это же и гарантирует,
   что новый инстанс не поднимется поверх старого дерева.

- **Новое поле конфига `stop-grace-secs`** (решение принято пользователем):
  целые секунды между сигналом группе и эскалацией до SIGKILL, дефолт 5
  (`DEFAULT_STOP_GRACE_SECS`). Kebab-имя — в стиле значений `restart`.
  Целые секунды по замыслу: TOML-integer не требует парсера длительностей, а
  отрицательные значения отсекает сам тип `u64`.
- **Техдолг Этапа 3 закрыт:** подряд идущие ошибки опроса считаются
  (`MAX_CONSECUTIVE_POLL_ERRORS = 20`, ~1 с при тике 50 мс); по исчерпании —
  best-effort `killpg(SIGKILL)`, финальная попытка реапа, `done = true` и лог
  уровня `error`. Счётчик сбрасывается при любом успешном опросе. Exit-код
  супервизора не трогается: сдача отражается только в логе.
- **Тесты.** `tests/tree.rs` (реальный бинарник): `shutdown_kills_whole_tree` —
  заглушка форкает двух долгоживущих внуков, **глухих к SIGTERM** (иначе тест был
  бы зелёным и при полностью отсутствующем sweep — он доказывал бы только
  групповой форвардинг), после SIGTERM супервизору все три pid-а обязаны исчезнуть;
  `sigkill_escalation_when_child_ignores_sigterm` — путь SIGKILL по дедлайну
  (`stop-grace-secs = 1`); `second_signal_escalates_immediately` — второй сигнал
  при grace 30 с, handshake через поллинг лога, а не sleep. `tests/shutdown.rs`
  (in-process, `FakeClock`): `escalation_waits_for_grace_deadline` (обе стороны
  дедлайна), `escalate_to_kill_skips_grace`, `leader_exit_sweeps_leftover_grandchildren`
  (тердаун на пути рестарта). Юниты: `spawned_child_leads_own_process_group`,
  `peek_exited_does_not_reap`, `poll_error_budget_exhausts_after_max`, парсинг
  `stop-grace-secs`.
  **Смерть внука наблюдается только поллингом с дедлайном:** прямого ребёнка
  реапит сам супервизор, а внука — init, асинхронно, и до этого момента он зомби,
  по которому `kill(pid, 0)` возвращает успех. Одиночный `assert` на `ESRCH`
  сразу после выхода супервизора — гарантированный флейк.
- **Критерий приёмки:** завершение супервизора не оставляет ни одного потомка
  дерева живым; зомби не накапливаются. ✅ — на всех штатных путях; единственное
  исключение перечислено ниже.

#### Известные ограничения Этапа 4

Перечислены явно, чтобы следующий проход не принял их за недоделку и не начал
«чинить» осознанные решения.

1. **Нет верхней границы на shutdown целиком.** Процесс, переживающий SIGKILL
   (D-state), оставляет супервизор в фазе `Killing` навсегда. Ошибку доставки
   SIGKILL мы ретраим раз в секунду (`KILL_RETRY`), но против D-state ретрай
   бессилен — там сигнал доставлен и просто не может быть обработан.
   Интеграционные тесты защищены `wait_with_timeout`, поэтому в CI это даёт
   красное, а не зависание. Финальный таймаут в Этап 5 не вошёл (этап трогает
   CLI и публикацию состояния, а не механику гашения) — остаётся кандидатом в
   POST-MVP.
2. **Путь сдачи по бюджету ошибок опроса может оставить зомби или сироту.**
   Исчерпав `MAX_CONSECUTIVE_POLL_ERRORS`, супервизор бьёт группу SIGKILL-ом,
   пробует дореапить лидера (10 попыток по 10 мс) и отпускает `Child`. Если
   реапинг не успел — остаётся зомби до выхода супервизора; если сам SIGKILL
   отказал — остаётся живая сирота. Оба исхода пишутся в лог явным
   `error`-сообщением, а не проглатываются. Ветка требует аномального errno от
   `waitid` (`SA_RESTART` исключает EINTR), поэтому дальше не укрепляем.
3. **`stop-grace-secs` не достаётся внукам, если лидер вышел раньше срока.**
   Прямое следствие правила «выход лидера ⇒ немедленный sweep» (обоснование
   выше). Практическая ловушка: `["/bin/sh", "-c", "myapp"]` без `exec` делает
   лидером шелл, тот умирает на SIGTERM мгновенно, и `myapp` добивается
   SIGKILL-ом через миллисекунды. Задокументировано в
   `examples/supervisor.toml`.
4. **Инвариант «зомби-лидер пиннит pgid» держится, пока лидер остаётся в своей
   группе.** Супервизируемый процесс, сам зовущий `setsid`/`setpgid` (классический
   демон с двойным форком), уходит из группы и из-под контроля супервизора.
   Без cgroups это принципиально нерешаемо; `Some(pgid)` — гарантия при
   добросовестном ребёнке, а не абсолютная.
5. **Ветка сдачи по бюджету ошибок не покрыта e2e-тестом.** Покрыта юнитом на
   `record_poll_error` и тестом, дёргающим `handle_poll_error` напрямую;
   инъекция errno в `waitid` мока не стоит.

#### Техдолг, найден на ревью Этапа 4

В отличие от списка выше (там — принятое поведение), это отложенные правки.
У каждой указан триггер пересмотра, чтобы решение «потом» не превратилось в
«никогда» и не всплыло заново как «находка».

Итог по входе в Этап 5: **три пункта из пяти сработали и закрыты**, два не
сработали и остаются в силе.

- ✅ **ЗАКРЫТО в Этапе 5. `child` и `pgid` — два `Option`, обязанных быть
  согласованными** (`supervise.rs`, структура `Supervised`). Триггер сработал:
  Этапу 5 понадобилось состояние процесса для `status`. Сделано первым шагом,
  до любого кода состояния: поля объединены в
  `running: Option<Running { child, pgid }>`, инвариант
  «`running.is_some()` ⇔ killpg безопасен» теперь выражен типом, мёртвые ветки
  `pgid: None` при живом ребёнке удалены. Порядок peek → killpg-sweep → reap и
  правило «обнулять только после реапинга лидера» сохранены дословно.
- ✅ **ЗАКРЫТО в Этапе 5. Параллельность гашения не проверена ни одним
  тестом.** Триггер сработал (рефактор трогает `begin_shutdown` и ветку
  дедлайнов в `tick()`), поэтому тест написан **до** рефактора и зелёный по обе
  стороны от него: `tests/shutdown.rs::shutdown_deadlines_are_per_process_not_shared`
  — два глухих к TERM стаба с `stop-grace-secs` 2 и 7, на `FakeClock`. На 3 с
  умирает только первый, на 8 с — второй; блокирующая `terminate_tree` уложилась
  бы в 2 + 7 = 9 с последовательно.
- ✅ **ЗАКРЫТО в Этапе 5. Рестарт после sweep не проверяет новый pgid.** Триггер
  сработал (рефактор трогает ветку респавна). Тест
  `tests/shutdown.rs::restarted_instance_leads_its_own_fresh_group`: стаб падает
  на первом запуске и остаётся жив на втором, тест дожидается **второй** строки
  pid-файла и поллингом с дедлайном проверяет `getpgid(pid2) == pid2`.
  Хелпер `wait_for_pid` в этом файле обобщён до `wait_for_pid_line(path, n, …)`,
  а старое имя оставлено тонкой обёрткой — новой копии не появилось.
- ❌ **НЕ СРАБОТАЛ. Три копии `wait_for_pid` в `tests/` с разошедшейся
  семантикой** (`signals.rs`, `shutdown.rs` — ждут одну строку;
  `tree.rs::wait_for_pids` — парсит все и закрывает окно open/write).
  Дублирование между интеграционными крейтами осознанное, но расхождение
  контрактов — заявка на то, что следующая правка попадёт в одну из трёх.
  **Триггер:** появление четвёртой копии. В Этапе 5 четвёртой копии не
  появилось намеренно: e2e-тесты `tests/status.rs` делают handshake по файлу
  состояния (`wait_for_state`), а не по pid-файлу.
- ❌ **НЕ СРАБОТАЛ. `wait_until_gone` считает `EPERM` за «жив»** и уязвим к
  переиспользованию pid в окне поллинга. Чинить нечем — это фундаментальное
  ограничение проверки по pid; ошибка даёт **красное, а не зелёное**, то есть
  флейк, а не потерю покрытия. Записано, чтобы при разборе будущего флейка не
  искать баг в супервизоре. Этап 5 добавил второго носителя того же
  ограничения — `state::daemon_alive` (см. ограничение 1 Этапа 5).

### Этап 5 — CLI статуса (готово)

**Три решения приняты пользователем на входе в этап и здесь только фиксируются.**

1. **Канал — файл состояния, а не unix-socket.** Демон периодически пишет
   снапшот, `status` его читает. Прямое следствие: **условие пересмотра из
   Этапа 3 не сработало** — цикл остаётся поллинговым, будить нечего, поэтому
   `src/signal.rs` (глобальный `AtomicI32` + `take_pending()` в `run()`) не
   тронут, self-pipe/`signalfd` не вводились.
2. **Чистый переход на подкоманды, без обратно-совместимого алиаса.** Форма
   «единственный позиционный аргумент = путь к конфигу» упразднена; см.
   актуализированный критерий приёмки Этапа 1.
3. **Разбор аргументов — ручной, по `std::env::args`.** Ни `clap`, ни его
   аналогов: две подкоманды и один флаг не окупают зависимость. Новых крейтов
   этап не добавил вовсе; единственная правка `Cargo.toml` — фича `"user"` у
   уже имевшегося `nix` (нужна `Uid::current()` для дефолтного пути).

- **CLI** (`src/cli.rs`, чистая `parse(&[String]) -> Result<Command,
  UsageError>`, юнит-тестируемая; `main.rs` — тонкая обвязка):
  - `supervisor-rs run <config-path> [--state-file <path>]` — демон;
  - `supervisor-rs status [--state-file <path>]` — таблица состояния;
  - `-h`/`--help` в любой позиции побеждает всё, печатается в **stdout**,
    exit 0; usage-ошибка идёт в stderr с текстом помощи и даёт exit 2;
  - `--state-file` есть у обеих подкоманд; повторный флаг — последний
    побеждает; env-переменную не вводили, одного механизма достаточно.
- **Файл состояния** (`src/state.rs`):
  - **Формат — TOML.** `serde` + `toml` уже в зависимостях, значит ноль новых
    крейтов; формат человекочитаем и совпадает с форматом конфига. Отвергнуты
    JSON (потребовал бы `serde_json` ради ничего) и самописный line-формат
    (парсер и экранирование имён руками).
  - Схема: `version` (несовпадение → отказ, а не догадки), `daemon-pid`,
    `written-at-unix-secs` (информационное поле, решений по нему не
    принимается — поэтому wall-clock здесь не ломает детерминизм тестов),
    массив `[[process]]` с `name` / `state` (`running` | `restarting` |
    `stopping` | `stopped`) / `pid` / `restart-count` / `uptime-secs`.
    `pid` и `uptime-secs` отсутствуют, если инстанса нет.
  - **Путь по умолчанию:** `$XDG_RUNTIME_DIR/supervisor-rs/state.toml`, при
    незаданном (или пустом) `XDG_RUNTIME_DIR` —
    `/tmp/supervisor-rs-<uid>/state.toml`. Директория создаётся при записи с
    mode `0700`: путь в общем `/tmp` предсказуем, и world-writable родитель
    позволил бы чужому uid перехватить снапшот.
  - **Запись атомарна:** сериализация в строку → временный файл
    `state.toml.tmp` **в той же директории** (rename атомарен только внутри
    одной ФС) → `fs::rename` поверх. Читатель видит либо старый файл целиком,
    либо новый целиком; парс-ошибка у `status` поэтому означает реальную порчу,
    а не гонку с писателем. Имя tmp фиксированное — писатель ровно один, а
    `tempfile` остаётся dev-зависимостью. `fsync` не делаем: защищаемся от
    читателя-наблюдателя, а не от потери файла при падении ядра.
  - **Жизненный цикл:** первая запись — сразу на первой итерации `run()`,
    чтобы `status` работал практически немедленно после старта; дальше раз в
    `STATE_WRITE_INTERVAL = 1 c` (для человеческого CLI свежести в секунду
    достаточно, а запись на каждом 50-мс тике — 20 записей/с бессмысленного
    IO). Отсюда контракт: **данные `status` не старше 1 с**. Запись по
    событиям в v1 не делалась. При штатном завершении демона файл удаляется,
    поэтому «нет файла» = «демон не запущен».
  - **Ошибка записи не останавливает супервизию:** каждая неудача — `warn` в
    лог, демон продолжает работать (супервизия первична, `status` вторичен).
    Частота лога ограничена самим интервалом записи.
- **Интеграция в `SupervisorLoop`** (`supervise.rs`): `with_state_file(path)`
  (opt-in — тесты, которым файл не нужен, не трогают ФС), чистый `snapshot()`
  и `maybe_write_state()`, вызываемый в `run()` **после `tick()`**. `tick()` не
  трогали вовсе: инвариант «tick свободен от сайд-каналов и блокирующих sleep»
  сохранён. Интервал считается по инъектируемым часам, поэтому обе его стороны
  проверяемы на `FakeClock`.
- **Семантика `status`** (порядок проверок): нет файла → «not running»;
  незнакомая версия → «unsupported version»; IO/parse → «failed to read»;
  файл есть, но `kill(daemon-pid, 0)` даёт ESRCH → «stale». Все четыре — exit 1.
  Иначе таблица в stdout и exit 0. Устаревший файл `status` **не удаляет**: это
  read-only команда, чужие файлы она не трогает.
- **Exit-коды:** таблица Этапа 3 не изменилась (usage → 2, ошибка конфига → 1,
  `had_start_errors` → 1, иначе 0); `status` добавил только собственную 1 —
  «нечего показывать».
- **Тесты.** Юниты: `src/cli.rs` (14 кейсов на грамматику, включая смерть старой
  формы), `src/state.rs` (roundtrip, сериализация `None`, атомарность, версия,
  дефолтный путь через чистую `default_path_from`, `daemon_alive`).
  In-process: `tests/state.rs` — немедленность первой записи, троттлинг по
  интервалу на `FakeClock`, отражение всех четырёх состояний в снапшоте,
  удаление файла при выходе `run()`. E2e на реальном бинарнике:
  `tests/status.rs` — живой демон / его завершение, устаревший файл, чужая
  версия; `tests/cli.rs` — exit-коды и usage.
  **Правило этапа:** каждый тест, запускающий бинарник, обязан передавать
  `--state-file` в свой tempdir — иначе параллельные тесты дерутся за общий
  дефолтный путь (см. ограничение 2 ниже).
- **Критерий приёмки:** `supervisor-rs status` на запущенном демоне печатает по
  строке на процесс с именем, состоянием, PID, числом рестартов и uptime; на
  незапущенном (нет файла либо файл остался от умершего демона) — внятная
  ошибка в stderr и exit 1. ✅ —
  `tests/status.rs::status_shows_running_process_and_detects_daemon_exit`.

#### Известные ограничения Этапа 5

Как и у Этапа 4 — осознанное поведение, а не недоделки.

1. **Различение «файл устарел» по `daemon-pid` уязвимо к переиспользованию
   pid.** `state::daemon_alive` — это `kill(pid, 0)`, где `EPERM` считается за
   «жив». Если демон умер аварийно (SIGKILL, паника) и его pid успело получить
   постороннее приложение, `status` покажет устаревший снапшот как живой. Это
   тот же класс ограничения, что у `wait_until_gone` из Этапа 4: проверка
   живости по pid принципиально не race-free без `pidfd`, а вводить `pidfd_open`
   ради второстепенной команды — несоразмерно. Практическая вероятность мала
   (нужен именно аварийный конец демона плюс полный оборот счётчика pid), а
   штатный выход демона файл удаляет и вопрос снимает.
2. **Дефолтный путь файла состояния — один на uid.** Два демона с разными
   конфигами, запущенные без `--state-file`, пишут в один и тот же
   `$XDG_RUNTIME_DIR/supervisor-rs/state.toml`: последний писатель побеждает, а
   штатный выход одного удалит файл, на который смотрит `status` другого.
   Осознанно: v1 — «один супервизор на пользователя», как у user-инстанса
   systemd, и вводить `--instance`/именование ради гипотетического второго
   демона рано. Кто действительно запускает два — передаёт `--state-file`
   явно; ровно это и делают все тесты, поэтому параллельный тест-раннер
   изолирован.
3. **Процессы, чей первый spawn провалился, в `status` не видны.** Прямое
   следствие best-effort старта Этапа 2: такой процесс не попадает в `procs`,
   значит и в снапшот. Отражён exit-кодом 1 демона и `error`-логом при старте.
4. **Свежесть данных — до `STATE_WRITE_INTERVAL` (1 с).** `status` печатает
   снапшот на момент последней записи, а не на момент вызова. Записи по
   событиям в v1 нет.

Подкоманды `stop` / `restart <name>` и полноценный control-socket — POST-MVP на

### Этап 6 — Control-socket (готово)

**Решение пользователя, не пересматривать: control-socket встроен в
существующий поллинговый `run()`, событийный цикл (self-pipe/`signalfd`/`poll(2)`
по дескрипторам) не вводится.** `UnixListener` в неблокирующем режиме
(`set_nonblocking(true)`), `try_accept()` опрашивается раз в тик из `run()` —
тот же паттерн, что `maybe_write_state()` в Этапе 5: неблокирующая операция,
вызываемая из `run()` после `tick()`, не из самого `tick()`. `src/signal.rs`
(глобальный `AtomicI32`, `take_pending()`) не тронут вовсе. Цена — задержка
ответа на команду до одного тика (50 мс), осознанно приемлемая для
админ-CLI — ровно как латентность сигналов в Этапе 3.

- **Протокол — однострочный текстовый, новый модуль `src/control.rs`.**
  `<verb> <name>\n`, `verb` ∈ `start`/`stop`/`restart`, имя — всё после первого
  пробела до `\n` (`split_once(' ')`, не `split_whitespace`, — имя из конфига
  может содержать пробелы). Ответ — ровно одна строка: `ok`, `ok: <text>` или
  `error: <text>`, после чего сервер закрывает соединение. Одна команда — одно
  соединение, без сессий и пайплайнинга. Решение консистентно с Этапом 5: JSON
  добавил бы `serde_json` ради словаря из трёх глаголов, версионирование
  протокола не нужно — клиент и сервер всегда один и тот же бинарник.
  `MAX_REQUEST_BYTES = 4096`; запрос без `\n` длиннее лимита отбрасывается с
  `error: malformed request`.
- **Путь сокета** — тот же каталог, что у файла состояния (0700, вся модель
  доступа): `$XDG_RUNTIME_DIR/supervisor-rs/control.sock`, фолбэк
  `/tmp/supervisor-rs-<uid>/control.sock`. Переопределяется `--control-socket
  <path>` у `run` и у трёх клиентских подкоманд; env-переменной нет, по
  прецеденту `--state-file`. Общая XDG-логика вынесена в чистую
  `state::runtime_dir_from(xdg) -> PathBuf`, от которой теперь наследуются и
  `state::default_path_from`, и `control::default_socket_path_from` — рефактор
  без изменения поведения существующих юнитов Этапа 5.
- **Осиротевший сокет — probe-then-bind.** `bind` на существующий путь падает с
  `EADDRINUSE` независимо от того, жив ли владелец, поэтому `ControlServer::bind`
  сначала пробует `UnixStream::connect(path)` на существующий файл: успех →
  живой демон → `BindError::AlreadyRunning`; отказ (`ECONNREFUSED` и подобные) →
  файл осиротел, `fs::remove_file` + обычный `bind`. Живость доказывается самим
  сокетом, а не `daemon-pid` из state-файла (тот может отсутствовать, быть от
  другого `--state-file` или быть устаревшим) — и не делит с `daemon_alive`
  уязвимость к переиспользованию pid. Гонка «два демона стартуют одновременно и
  оба видят осиротевший файл» осознанно не закрыта — тот же класс ограничения,
  что «один супервизор на uid» из Этапа 5. Bind в `main.rs` делается **до**
  `SupervisorLoop::new` (до первого spawn): отказ «уже запущен» не должен успеть
  наплодить детей.
- **Ограниченно-блокирующие таймауты чтения/записи на принятом стриме** — второе
  (после `handle_poll_error`'а Этапа 4) санкционированное исключение из «цикл не
  блокирует». `try_accept` неблокирующий, но принятая коннекция в момент
  `accept` может ещё не нести данных; вместо per-connection буфера между тиками
  — `set_read_timeout`/`set_write_timeout` = `REQUEST_IO_TIMEOUT = 250 мс` на
  стриме и блокирующее чтение. Воспитанный клиент (наш же бинарник) пишет
  команду одним `write` сразу после `connect`, так что таймаут в штатной жизни
  не срабатывает; задержать цикл на 2×250 мс может только злонамеренный клиент
  того же uid — а такой uid может и SIGKILL демону послать напрямую. Это
  `SO_RCVTIMEO`/`SO_SNDTIMEO` уровня ОС, не логическое время — **API
  `Clock`/`FakeClock` не расширялось**. Обработка — не более одного соединения
  за тик; второй клиент получает ответ тиком позже.
- **`UserIntent` — новое измерение, ортогональное и `StopPhase`, и
  `shutting_down`.** `StopPhase` (TERM → дедлайн → KILL) переиспользован
  как есть для гашения по команде — второй такой машины не появилось. Но
  «что делать после реапинга» (рестартить по policy / не рестартить / рестартить
  принудительно) не помещается ни в `StopPhase` (обнуляется при реапинге), ни в
  `shutting_down` (режим всего супервизора, а команда адресна одному процессу).
  Поле `intent: UserIntent` в `Supervised` — `None` (обычная policy) /
  `Stopped` (нет респавна, `done` остаётся `false`, чтобы `start` мог оживить) /
  `RestartPending` (одноразовый принудительный респавн, затем `None`).
  Инвариант: `intent == Stopped ⟹ next_restart_at == None`. Процесс,
  остановленный оператором, не становится `done` — иначе `stop` единственного
  процесса завершил бы весь демон и `start` было бы уже некому принимать.
- **`handle_command(&mut self, req: &Request) -> Response`** (`supervise.rs`) —
  чистая по отношению к сокетам таблица переходов по пяти классам состояния
  процесса (RUNNING / STOPPING / BACKOFF / USER_STOPPED / DONE) × три глагола;
  `pub`, чтобы in-process тесты гоняли команды без всякого IO. Решения таблицы:
  - **Ответ — асинхронный ack, не подтверждение смерти или воскрешения.**
    `ok: stopping` значит «сигнал послан, `StopPhase` взведена», семантика
    `systemctl --no-block`; прогресс наблюдается через `status`.
  - `stop`/`start` идемпотентны (повтор — `ok`, как у systemctl); `restart`
    остановленного — ошибка с указанием на `start`.
  - `start`/`restart` из BACKOFF делают ближайший рестарт немедленным
    (`next_restart_at = now`), не сбрасывая текущую ступень backoff — команда
    ускоряет один рестарт, не объявляет процесс здоровым.
  - `start`/`restart` не спавнят синхронно — только выставляют
    `next_restart_at`; сам spawn делает существующая ветка респавна `tick()` на
    следующем тике, бесплатно наследуя её обработку ошибок, инкремент
    `restart_count` и установку `started_at`/`pgid`. Следствие: `restart_count`
    растёт и от операторских команд.
  - `DONE` не оживляется никогда: `done` — терминальный контракт `run()`,
    ревив сделал бы «все done → выход» ложным задним числом.
  - Правка `tick()` — ровно одна ветка, в обработке `PollOutcome::Exited`
    после `proc.running = None; proc.stop = Idle;`: вне `shutting_down` теперь
    матчится `proc.intent` (`RestartPending` → снять интент и поставить
    `next_restart_at = now`; `Stopped` → ничего не спавнить, лог; `None` —
    прежняя policy-ветка дословно). Порядок peek → killpg-sweep → reap в
    `poll_child` не тронут вовсе.
- **CLI** — один вариант `Command::Control { request: control::Request,
  control_socket }` вместо трёх зеркальных: `main.rs` обрабатывает их
  одинаково, глагол уже выражен типом `Request`. Флаги теперь проверяются на
  применимость к подкоманде (`--state-file` у `start`/`stop`/`restart` и
  `--control-socket` у `status` — usage-ошибка); раньше парсер собирал флаги до
  диспетчеризации и не проверял совместимость вовсе. Имя с `\n`/`\r` или
  пустое — usage-ошибка («process name must be a single line»): протокол не
  может выразить перевод строки в имени, инъекция отклоняется на клиенте.
  `control::send_command` — connect → один `write` строки запроса → один
  `read_line` ответа, оба направления с `CLIENT_IO_TIMEOUT = 5 c`, чтобы
  зависший демон не подвесил CLI.
- **Exit-коды** — существующая таблица без новой нумерации: usage → 2 (включая
  все новые грамматические ошибки); ошибка bind control-socket у `run` → 1
  (новый член класса «ошибка старта», тот же путь, что ошибка конфига);
  `start`/`stop`/`restart` — 0 при `ok`-ответе, 1 при `error:`-ответе или
  ошибке подключения.
- **Тесты.** Юниты `src/control.rs` (14: протокол, дефолтные пути, `bind`/
  `try_accept`/roundtrip/таймаут через реальные `UnixListener`/`UnixStream` в
  tempdir с короткими именами файлов — см. граблю `sun_path` ниже); юниты
  `src/cli.rs` (11 новых: грамматика `start`/`stop`/`restart`,
  `--control-socket`, применимость флагов, многострочное имя). In-process
  `tests/commands.rs` (16: `handle_command` + `tick()` на `FakeClock`, без
  сокетов вовсе — ключевой `stop_kills_process_and_policy_always_does_not_resurrect_it`
  доказывает, что `stop` побеждает policy `always`; на ревью добавлены
  `restart_twice_reports_already_in_progress` — вторая ветка STOPPING×restart
  из таблицы, недостающая в первой реализации, — и
  `commands_on_done_process_are_refused`, закрывающая весь класс
  DONE × {stop, start, restart}). E2e `tests/control.rs` (7,
  реальный бинарник): `stop_start_restart_roundtrip` — критерий приёмки этапа
  целиком (stop останавливает вопреки `always`, start возвращает с новым pid,
  restart меняет pid работающего); ошибочные пути (неизвестное имя, нет
  демона, команда во время shutdown); жизненный цикл сокета (удаление на
  чистом выходе, старт поверх осиротевшего файла, отказ на занятом). Каждый
  e2e-тест изолирует **и** `--state-file`, **и** `--control-socket` в своём
  tempdir. Все 96 тестов Этапов 1–5 проходят без поведенческих правок: четыре
  файла (`signals.rs`, `tree.rs`, `cli.rs`, `status.rs`) потребовали добавить
  `--control-socket` в свои хелперы запуска демона — иначе они конкурировали
  за один дефолтный путь сокета с любым другим тестом/демоном на той же
  машине (тот же класс проблемы, что «один супервизор на uid» из Этапа 5).
  `status.rs` был пропущен на кодинге и найден независимым ревью.
- **Известные ограничения Этапа 6** (осознанное поведение, не «чинить»):
  1. Гонка одновременного двойного старта на осиротевшем сокете не закрыта —
     тот же класс, что «один супервизор на uid» из Этапа 5.
  2. `status` не различает «остановлен оператором» и «завершился терминально»:
     оба состояния попадают в `stopped` снапшота, схема `version = 1` не
     менялась; различение отложено.
  3. `DONE` не оживляется никогда командой — только рестарт демона.
  4. Процесс, чей первый spawn провалился (best-effort старт Этапа 2), в
     `procs` отсутствует и отвечает «no such process» на любую команду — то же
     ограничение, что у `status`.
  5. `restart_count` растёт и от операторских `start`/`restart`, не только от
     policy-рестартов.
  6. Не более одного принятого соединения за тик; второй клиент отвечается
     тиком позже.
  7. Имя процесса с `\n` неадресуемо через control-socket — отклоняется на
     клиенте как usage-ошибка.
- **Не в скоупе v1** (записано, не реализовывать): параллельные клиенты в один
  тик (очередь остаётся в backlog ядра), `status`/список процессов через
  сокет, оживление `DONE`, различение `stopped`-оператором в `status`,
  аутентификация сверх 0700-каталога, `--instance`, перезагрузка конфига без
  рестарта демона (реализована в Этапе 8 через SIGHUP; команды `reload` в
  сокете по-прежнему нет).
- **Критерий приёмки:** на живом демоне с policy `always` `stop web` переводит
  `status` в `stopped` (`pid == None`) и процесс не воскресает; `start web`
  возвращает `running` с новым PID; `restart web` меняет PID работающего
  процесса. Команда на несуществующее имя, на остановленный демон и во время
  shutdown даёт внятную ошибку и exit 1 у клиента, не панику. ✅ —
  `tests/control.rs::stop_start_restart_roundtrip` и соседние тесты ошибочных
  путей.

### Этап 7 — Health-checks (готово)

В MVP «жив» = «процесс существует» (peek по pid). Этап 7 добавляет активные
проверки здоровья: одна опциональная проба на процесс — **exec** (команда,
успех по коду выхода 0), **tcp** (порт принимает соединение) или **http**
(эндпоинт отвечает 2xx). `failure-threshold` неуспехов **подряд** форсирует
рестарт даже живого, но «залипшего» процесса — через ту же машину
TERM → grace → SIGKILL, что и операторский `restart` Этапа 6.

**Решение пользователя, не пересматривать: пробы выполняются
ограниченно-блокирующе, ровно одна проба за тик.** Тот же паттерн, что
control-socket Этапа 6 (`try_accept` + bounded `set_read_timeout`) и
`handle_poll_error` Этапа 4 (реальный retry-sleep в цикле) — **третье**
санкционированное исключение из «цикл не блокирует»: один тик может
блокироваться на время таймаута одной пробы (`timeout-secs`). Если срок настал
у нескольких проб разом, за тик исполняется одна (первая по порядку `procs`),
остальные — на следующих тиках, так что цикл никогда не блокируется на сумму
нескольких таймаутов. Таймаут пробы — реальное время ОС (`connect_timeout` /
`SO_RCVTIMEO` / дедлайн по `std::time::Instant`), **API `Clock`/`FakeClock` не
расширялось**; по инъектируемым часам едет только *расписание* (когда проба
должна случиться), как у `maybe_write_state`.

**Решение пользователя, не пересматривать: HTTP-проба — самописный минимальный
HTTP/1.1 GET поверх `std::net::TcpStream`, без внешнего HTTP-крейта.** Запрос
собирается вручную (`GET {path} HTTP/1.1\r\nHost: {ip}:{port}\r\nConnection:
close\r\n\r\n`), читается только статус-строка, успех — код `2xx` (3xx — уже
неуспех, редиректов нет by design). Без TLS, chunked, keep-alive. **Этап не
добавляет ни одной новой зависимости в `Cargo.toml`** — то же обоснование, что
TOML вместо `serde_json` и line-протокол вместо фреймворка в Этапах 5–6:
словарь HTTP-пробы — одна строка запроса и три цифры кода ответа, крейт ради
этого не окупается.

**Скоуп: одна liveness-проба, без триады startup/readiness/liveness из
POST_MVP_PLAN.** Обоснование: readiness в k8s управляет маршрутизацией трафика
— у supervisor-rs нет балансировщика; startup-пробу здесь заменяет
`start-period-secs` (одно поле вместо второй пробы со своим расписанием);
liveness — единственный вид, чьё действие (рестарт) вообще есть в арсенале
супервизора.

- **Конфиг — секция `[process.health-check]` (`src/config.rs`), одна
  подтаблица, не массив** (одна проба на процесс в v1):

  ```toml
  [process.health-check]
  type = "http"                # exec | tcp | http — обязательное
  port = 8080                  # tcp/http: обязательное
  path = "/health"             # http: default "/"
  # host = "127.0.0.1"         # tcp/http: default 127.0.0.1, только IP-адрес
  interval-secs = 10           # default 10
  timeout-secs = 5             # default 5
  failure-threshold = 3        # default 3
  start-period-secs = 15       # default 0
  ```

  Разбор — «сырая» `HealthCheckConfig` (serde) → ручная валидация в
  типизированный `HealthProbe` (`probe()`), не `#[serde(flatten)]` +
  internally-tagged enum (известная шершавая кромка serde/toml). Бесплатная
  валидация типами по прецеденту `stop-grace-secs`: `NonZeroU16/32/64` отсекает
  нули, `IpAddr` отсекает hostname. Правила `probe()`: `exec` требует непустой
  `command`, `host`/`port`/`path` запрещены; `tcp`/`http` требуют `port`,
  `command` запрещён; `http`-`path` обязан начинаться с `/`. Некорректная
  секция — `ConfigError::Invalid` при `load()` (exit 1), не паника в рантайме.
- **`host` — только `IpAddr`, DNS-резолвинг не поддержан.** У `std` нет
  резолвинга с таймаутом: `ToSocketAddrs` заблокировал бы поток на
  неограниченное время и пробил бы бюджет «тик не блокируется дольше таймаута
  одной пробы». `127.0.0.1` (дефолт) покрывает основной случай — процесс
  всегда локален. Hostname/DNS — кандидат в POST_MVP.
- **Раннер (`src/health.rs`)** — `run_probe(probe, timeout) -> Result<(),
  ProbeError>`, по одной приватной функции на вид пробы, бюджет один на всю
  пробу (не на каждый шаг): `let deadline = Instant::now() + timeout`, каждый
  следующий блокирующий шаг получает остаток. exec: три `Stdio::null()`,
  `try_wait()` в цикле поллинга; дедлайн истёк → `child.kill()` +
  обязательный `child.wait()` (иначе зомби на всё время жизни демона). tcp:
  `connect_timeout` + drop. http: см. выше, статус-строка читается побайтово с
  ограничением `MAX_STATUS_LINE_BYTES`, `set_read/write_timeout` не даёт
  нулевого значения — минимум 1 мс (у `std` `set_read_timeout(Some(ZERO))` —
  ошибка).
- **Расписание (`src/supervise.rs`).** `HealthState { probe, schedule:
  Option<HealthSchedule>, consecutive_failures }` на `Supervised`. Первая
  проба текущего инстанса — `started_at + start_period + interval` (при
  дефолтном `start-period-secs = 0` — через один интервал после старта:
  проверки в момент `t=0`, пока порт ещё не открыт, не бывает никогда).
  Последующие пробы — `next_check_at = clock.now() + interval`, назначается
  **после** завершения пробы. Перевзвод: `schedule.armed_for !=
  proc.restart_count` → расписание строится заново, счётчик неуспехов
  обнуляется — `restart_count` как генерация инстанса даёт рестарту любого
  происхождения (policy/оператор/health) чистый старт **без единой новой
  ветки** в `tick()`/`handle_command`. Остановленный оператором или гасящийся
  процесс (`running == None` или `stop != Idle`) пропускается, расписание не
  двигается. `run_due_health_check()` вызывается из `run()` после
  `poll_control()`, исполняет **не более одной** due-пробы за вызов.
- **Переход «залип → рестарт» — переиспользование, не параллельный путь.**
  Порог неуспехов достигнут → `proc.intent = UserIntent::RestartPending;
  signal_terminate(...)` — ровно то, что делает `handle_command` на RUNNING ×
  `restart` (Этап 6). Дальше работает существующая машина
  `StopPhase`/эскалация/`poll_child`/респавн без единой новой ветки.
  **Третий вариант интента (`UnhealthyRestart`) осознанно не введён** —
  продублировал бы арм `RestartPending` в `tick()` и потребовал бы решений по
  всей STOPPING-строке `handle_command` ради единственного наблюдаемого
  отличия (подписи одной строчки лога). Единственная правка `tick()` —
  текст лога в арме `RestartPending`: `"operator restart: respawn scheduled"`
  → `"forced restart: respawn scheduled"` (интент теперь взводит и health-
  механизм), плюс doc-комментарии `UserIntent`/`ProcClass::Stopping`. Backoff
  при health-рестарте не сбрасывается и не применяется — как у операторского
  `restart`; троттлинг перманентно нездорового процесса — сама каденция проб
  (минимум `start_period + threshold × interval`).
- **Тесты.** Юниты `src/health.rs` (14: по виду пробы, таймауты, реап
  убитого по таймауту exec-ребёнка) и `src/config.rs` (валидация секции,
  дефолты). In-process `tests/health.rs` (14: расписание/перевзвод/интеракции
  на `FakeClock`, без реальных проб) — ключевые
  `reaching_threshold_forces_restart` (рестарт ровно после N неуспехов
  подряд, не раньше) и `success_resets_consecutive_failures`. E2e
  `tests/health_e2e.rs` (3, реальный бинарник + реальные TCP/exec-пробы):
  `unhealthy_process_is_restarted_after_threshold`,
  `stuck_process_is_killed_via_grace_escalation` (SIGKILL по grace у
  залипшего), взаимодействие с операторским `stop`. Все 191 тест (было 147 до
  Этапа 7) проходят; единственная правка существующих — механическое
  `health_check: None` в литералах `ProcessConfig` во всех тестовых
  хелперах-`cfg()`.
- **Границы соблюдены:** `Cargo.toml`, `src/signal.rs`, `src/cli.rs`,
  `src/control.rs`, `src/main.rs`, схема state-файла (`version = 1`) —
  без правок.
- **Известные ограничения Этапа 7** (осознанное поведение, не «чинить»):
  1. Тик может блокироваться до `timeout-secs` одной пробы — на это время
     растёт латентность реакции на сигналы, команды сокета и другие пробы;
     ограничено одной пробой за тик.
  2. Health не отражён в state-файле/`status` отдельным полем — только логи и
     косвенно (`stopping`/`restarting`, рост `restart-count`); причина
     рестарта (оператор vs health) в `status` неразличима — тот же класс, что
     ограничение 2 Этапа 6.
  3. `host` — только IP-адрес; hostname/DNS не поддержан.
  4. exec-проба не получает своей process-группы: потомки зависшей и убитой
     по таймауту команды-пробы осиротеют. Команда пробы должна быть простой
     проверкой, не форкать демонов.
  5. HTTP: без TLS, редиректов, chunked, keep-alive; читается только
     статус-строка; stdout/stderr exec-пробы отбрасываются.
  6. Health-рестарт, как и операторский, не применяет backoff и
     инкрементирует общий `restart_count`.
  7. Одна проба на процесс; несколько проб и readiness/liveness-разделение —
     POST_MVP.
- **Не в скоупе v1**: startup/readiness-пробы отдельно от liveness, hostname/
  DNS в `host`, несколько проб на процесс, видимость health в `status`.
- **Критерий приёмки:** на живом демоне процесс со здоровой пробой работает
  нетронутым (`restart-count` не растёт); при проваливающейся пробе ровно
  после `failure-threshold` неуспехов подряд — не раньше — процесс
  перезапускается (новый PID и выросший `restart-count` в `status`), залипший
  вопреки SIGTERM добивается SIGKILL по `stop-grace-secs`. Успешная проба
  сбрасывает счётчик. Операторский `stop` останавливает и пробы; shutdown
  пробами не задерживается. ✅ — `tests/health.rs`, `tests/health_e2e.rs`.

### Этап 8 — Перезагрузка конфига (SIGHUP, готово)

До Этапа 8 конфиг читался ровно один раз, при `run <config>`; любое изменение
набора процессов требовало рестарта демона (а значит — teardown всех деревьев).
Этап 8 добавляет перезагрузку: по **SIGHUP** демон перечитывает **тот же файл**,
что был передан в `run`, сравнивает новый список `[[process]]` со старым **по
имени** и применяет только разницу. До Этапа 8 SIGHUP убивал демона диспозицией
по умолчанию — теперь перезагружает конфиг.

**Решения пользователя, не пересматривать:**

1. **Убранный** процесс останавливается как операторский `stop` (TERM → grace →
   SIGKILL) и после полного реапинга **удаляется из списка супервизии** и из
   `status` — в отличие от операторского stop, ему нечего делать в списке.
2. **Изменённый** (не равен по `PartialEq` хоть в одном поле: `command` / `env`
   / `workdir` / `restart` / `stop-grace-secs` / `health-check`) → немедленный
   принудительный рестарт через **переиспользование
   `UserIntent::RestartPending`** — тот же путь, что операторский `restart` и
   health-рестарт Этапа 7. Третьего варианта интента нет.
3. **Неизменённый** не трогается вообще: ни рестарта, ни сброса расписания/
   счётчиков health-проб, ни лишних info-логов.
4. **Новое имя** — спавнится сразу, как в `new()`.
5. **Битый новый конфиг** (ошибка парсинга TOML или `ConfigError::Invalid`) →
   reload отменяется целиком: `error!`-лог с причиной, старый конфиг и все
   процессы нетронуты, демон живёт. **Всё или ничего** — частичного применения
   не бывает.
6. **SIGHUP во время shutdown игнорируется** (как пробы в `run_due_health_check`).
7. **Scope — только SIGHUP.** Команды `reload` через control-socket нет.

**Технические решения, зафиксированные с постановкой:**

- **Отдельный атомик `RELOAD_PENDING: AtomicBool`** рядом с `PENDING`, а не
  третье значение в `AtomicI32`: `PENDING` хранит только *последний* сигнал, и
  SIGHUP, попавший туда, мог бы затереть одновременный SIGTERM/SIGINT — потеря
  сигнала остановки недопустима. `handle_signal` ветвится по `signo == SIGHUP`
  перед единственной атомарной записью (сравнение async-signal-safe).
- **`Supervised.config` — владеющий `Arc<ProcessConfig>` вместо `&'a`
  заимствования**: новый `Vec<ProcessConfig>`, прочитанный по SIGHUP, живёт
  меньше исходного среза `configs`, так что reload с заимствованием невозможен в
  принципе. Лайфтайм-параметр `'a` убран из `SupervisorLoop`/`Supervised`;
  внешняя сигнатура `new(configs: &[ProcessConfig], …)` не изменилась (внутри
  каждый конфиг оборачивается в `Arc`). `Arc::clone` дёшев, `ProcessConfig`
  иммутабелен после загрузки — shared ownership без внутренней мутабельности.
- **Diff по имени + `PartialEq`**: сравнение по значениям структуры, а не по
  тексту файла — перестановка секций, комментарии и форматирование изменением не
  считаются; `env` — `BTreeMap`, порядок ключей не важен. **Дубликаты имён —
  ошибка загрузки** (`ConfigError::Invalid`), в т.ч. при первом старте: diff по
  неуникальному ключу неопределён. Ужесточение относительно Этапов 1–7.
- **Путь к конфигу — opt-in поле `reload_path`** по прецеденту
  `state_writer`/`control_server` (builder `with_config_reload(path)`): тесты, не
  вызывающие его, на SIGHUP не реагируют. Сам diff+apply — `pub fn apply_config`,
  чтобы in-process тесты гоняли его на `FakeClock` без файлов и сигналов;
  `reload_config` только читает файл поверх него.

**Таблица судеб** (класс состояния × вид изменения):

| Класс \ вид | unchanged | changed | removed |
|---|---|---|---|
| RUNNING (`stop == Idle`) | ничего | `RestartPending` + TERM (= операторский `restart`) | `Stopped` + TERM, пометка на удаление |
| STOPPING (`stop != Idle`) | ничего | только подмена `Arc` (стоп в полёте сам респавнит/останавливает) | пометка на удаление, TERM не шлётся второй раз |
| BACKOFF | ничего | `next_restart_at = now` (backoff-ступень не сбрасывается) | пометка + удаление сразу (реапить нечего) |
| USER_STOPPED | ничего | только подмена `Arc` (оператор побеждает: не запускается) | удаляется даже остановленный (имени больше нет) |
| DONE | ничего | подмена `Arc` (косметика), **не оживляется** | удаляется сразу |

У изменённого процесса при подмене конфига `HealthState.probe` **пересобирается**
(`build_health`): перевзвод по generation в `run_due_health_check` сбрасывает
только `HealthSchedule`, а `probe` строится один раз в `new()` и иначе бы
осталась старой вечно — изменённая секция `[process.health-check]` покрыта, как и
добавление (None → Some) и удаление (Some → None). Новый `stop-grace-secs`
применяется уже к *текущему* стопу: `Arc` подменяется **до** `signal_terminate`.

**Двухфазное удаление**: `Supervised.pending_removal: bool` ставится при apply,
физический `retain` — только когда `running == None` (реапить нечего),
`prune_removed()` вызывается в конце `apply_config` (для мёртвых записей — сразу,
без тика) и в конце `tick()` (для живых — после TERM → grace → SIGKILL → реапинг).
Повторное добавление имени во время удаления (TERM в полёте) воскрешает запись:
снимается пометка, подменяется конфиг, интент → `RestartPending`.

**Схема state-файла НЕ меняется, `version` остаётся 1**: убранный процесс
исчезает из снапшота как следствие удаления из `procs` (до реапинга виден как
`stopping`), изменённый проходит обычный `stopping → restarting → running` —
неотличим от операторского `restart`. Логи — единственный прямой канал
наблюдения reload'а: `info!` на приём SIGHUP, `error!` на отклонённый конфиг,
per-process `info!` на removed/changed/added, итоговая строка со счётчиками
(или `config reload: no changes`).

- **Известные ограничения** (осознанные):
  1. Только SIGHUP; команды `reload` через сокет нет — кандидат в POST_MVP.
  2. Reload применяется не мгновенно: живые изменённые/убранные идут через
     TERM → grace → SIGKILL, полное применение занимает до их `stop-grace-secs`;
     «применён» наблюдается через `status`/логи (у SIGHUP нет ответа).
  3. `done`-процесс не оживляется reload'ом никогда — инвариант «DONE не
     оживляется» Этапа 6; лечится только рестартом демона.
  4. Изменение конфига user-stopped процесса не запускает его — оператор
     побеждает; новый конфиг подхватит будущий `start <name>`.
  5. Неудавшийся spawn добавленного — best-effort: `error!`-лог, без трекинга и
     ретраев (как в `new()`); `had_start_errors` и exit-код демона reload не
     трогает.
  6. Рестарт изменённого инкрементирует общий `restart_count` и не применяет/не
     сбрасывает backoff — в `status` неотличим от операторского.
  7. Переименование = «убрать + добавить»: старое дерево гасится, новое стартует
     с нуля, без переноса состояния.
  8. Reload, убравший все процессы, штатно завершает демона после teardown
     (пустой `procs` ⟹ `any_active() == false`) — симметрично «все стали `done`».
  9. Дубликаты имён теперь отклоняются на загрузке — ужесточение относительно
     Этапов 1–7, цена корректного diff-ключа.
  10. Латентность реакции на SIGHUP — до одного тика (50 мс) плюс, в худшем
      случае, длительность блокирующих операций текущей итерации (проба
      health-check) — тот же класс, что у SIGTERM.
- **Не в скоупе**: команда `reload` в сокете (кандидат в POST_MVP), оживление
  DONE, запуск user-stopped по изменению конфига, ретраи неудавшегося spawn'а.
- **Критерий приёмки:** на живом демоне правится файл (один процесс неизменён, у
  одного изменена команда, один убран, один добавлен) и посылается
  `kill -HUP <pid>`. После этого в `status`: неизменённый — тот же PID и
  `restart-count`; изменённый — новый PID, выросший `restart-count`, новая
  команда; убранный — исчез (дерево мертво); добавленный — `running`. `kill -HUP`
  с испорченным файлом ничего не меняет и не роняет демона (`error` в логе).
  SIGHUP во время shutdown игнорируется; SIGTERM после reload гасит всё и даёт
  exit 0. ✅ — `tests/reload_e2e.rs::sighup_applies_diff` (все четыре судьбы за
  один HUP), `tests/reload.rs` (in-process на `FakeClock`),
  `tests/reload_e2e.rs::sighup_with_broken_config_changes_nothing`.

### Этап 9 — Ротация логов (захват stdout/stderr, ротация по размеру, готово)

- **Что делает.** Опциональная секция `[process.log]` на процесс задаёт захват
  вывода в файлы с ротацией по размеру, целиком внутри супервизора. Без секции
  поведение прежнее до байта: stdio наследуется (`Stdio::inherit()`), ноль новых
  механик — opt-in по прецеденту `[process.health-check]` Этапа 7. С секцией
  сконфигурированный поток (stdout, stderr или оба, раздельные файлы) идёт через
  pipe в супервизор; отдельный поток ОС на каждый захваченный поток читает pipe и
  дописывает в текущий файл; при достижении `max-size-bytes` выполняется сдвиг
  `<path>.{keep-1}`→`.keep`, …, `<path>`→`.1` и открывается новый пустой текущий
  файл. Хранится не более `keep` ротированных плюс текущий. Поля: `stdout-path`,
  `stderr-path` (оба `Option`, хотя бы один обязателен, различны и глобально
  уникальны между процессами), `max-size-bytes` (`NonZeroU64`, default 10 MiB),
  `keep` (`NonZeroU32`, default 5). Невалидная секция (нет пути, совпадающие или
  дублирующиеся пути) — `ConfigError::Invalid` на загрузке, exit 1, существующий
  класс ошибки; не паника в рантайме.

- **Решения пользователя (приняты, не пересматривались).**
  1. Ротация — полностью в супервизоре, без внешних инструментов и сигналов;
     проверка размера — в момент записи, не по сигналу и не по интервалу.
  2. Механизм live-ротации — отдельный поток ОС на поток вывода, читающий из
     pipe, а не прямая запись ребёнка в файл. **Первое использование потоков в
     проекте.** Прямая запись + rename супервизором ломается: ребёнок пишет в
     унаследованный дескриптор, а после `rename` под открытым дескриптором тот
     продолжает писать в старый inode, новый `.log` остаётся пуст (переоткрывать
     stdout — не контракт ребёнка). Copy-truncate отвергнут: позиция записи
     открытого дескриптора не сбрасывается при `ftruncate`, первая же запись после
     truncate создала бы sparse-дыру размером в старый файл. Pipe даёт файлу ровно
     одного писателя — поток-читатель, он и ротирует.
  3. v1 ротирует только по размеру. Ротация по времени потребовала бы таймера в
     потоке-читателе — второго, реального таймера вне `Clock`/`FakeClock`,
     ненаблюдаемого в детерминированных тестах; остаётся кандидатом в POST_MVP.
  4. Без сжатия ротированных файлов (кандидат в POST_MVP).

- **Граница потоков и детерминизм.** Расписание и супервизия остаются
  однопоточным поллинг-циклом на `Clock`; захват вывода — по потоку на pipe, без
  часов вообще. Это не размывает `FakeClock`-детерминизм: ротация — функция
  *размера*, а не времени, поэтому потоки-читатели не касаются логического
  времени. Состояние ротации (текущий размер, файловый хендл) живёт целиком
  внутри потока-читателя; `Supervised` владеет только `JoinHandle`-ами.

- **Фд-гигиена write-конца pipe (критично).** `Command::spawn()` дублирует
  переданный `Stdio` в форкнутого ребёнка, но родительская копия write-конца
  живёт, пока жив её владелец. Здесь владелец — локальный `cmd` в `spawn()`:
  write-конец **перемещается** в `Stdio::from(write)` внутрь `cmd`, а `cmd`
  дропается на выходе из `spawn()`. После возврата write-конец держит только
  ребёнок (и внуки, унаследовавшие его через `fork()`), поэтому поток-читатель
  дождётся EOF. Утечка родительской копии = read-конец никогда не увидит EOF =
  поток висит вечно, и потоки копятся при каждом респавне. Тест
  `spawn_with_log_reaches_eof_after_child_exit` ловит эту регрессию (утёкший
  write-конец → вечно блокирующийся read → громко висящий тест). Используется
  `pipe()` (не `pipe2(O_CLOEXEC)`): `pipe2` за фичей `fs` крейта `nix`, а
  `Cargo.toml` заморожен; безопасно, потому что супервизор форкает строго
  однопоточно и последовательно — чужой `fork()` между `pipe()` и `cmd.spawn()`
  невозможен, write-конец закрыт до следующего спавна.

- **Сходимость EOF через killpg-sweep Этапа 4.** EOF на pipe наступает, когда
  закрыт *последний* write-конец, включая копии у внуков (проставить им CLOEXEC
  супервизор не может — чужое адресное пространство). Порядок Этапа 4 в
  `poll_child` (peek → killpg-SIGKILL-sweep всей группы → reap) сводит все копии к
  нулю: к моменту `PollOutcome::Exited` вся группа уже под SIGKILL. Отдельный
  «стоп-сигнал» потоку не нужен — teardown Этапа 4 и есть его протокол завершения.

- **Bounded join при реапинге (а не голый `join`).** Потоки-читатели
  присоединяются в момент реапинга лидера (`tick()` ветка `PollOutcome::Exited`
  и give-up путь `handle_poll_error`), а не при остановке демона: следующий
  инстанс открывает читателя на тот же путь, поэтому join до респавна — то, что
  сохраняет инвариант «один писатель на файл»; и тестам достаётся синхронная
  гарантия «pid реапнут ⟹ файл полон». Join **ограниченный** (поллинг
  `JoinHandle::is_finished()` с реальным дедлайном `LOG_JOIN_RETRIES ×
  LOG_JOIN_RETRY_DELAY` = 1 с, детач по таймауту): потомок, сбежавший из
  process-группы собственным `setsid`, недостижим для killpg (известное
  ограничение Этапа 4 «живой орфан») и держал бы write-конец, а голый `join()`
  подвесил бы `tick()`, а с ним весь демон, навечно. Реальное время, как
  `REAP_RETRIES`: ждём доставку SIGKILL ядром и последние записи читателя, а не
  логическое время — `FakeClock` это не пропускает. Четвёртое санкционированное
  исключение из «цикл не блокирует» (после `handle_poll_error`, таймаута сокета и
  таймаута пробы).

- **Drain-first политика ошибок IO.** Ошибка записи в лог-файл (полный диск,
  удалённая директория) никогда не останавливает чтение pipe: чанк отбрасывается
  с warn-логом (только на смену состояния ok→err) и ленивым переоткрытием, но
  pipe дочитывается до EOF всегда. Иначе живой write-конец при остановленном
  читателе заблокировал бы ребёнка на полном 64 KiB-буфере pipe, а дроп read-конца
  доставил бы ребёнку SIGPIPE и убил его.

- **Наблюдаемость и state-файл.** Схема state-файла не изменена, `version`
  остаётся 1 (прецедент health Этапа 7: статус тоже не в снапшоте). Пути логов и
  состояние ротации в `status` не отражаются — лог наблюдаем самим лог-файлом.
  `tracing` — единственный канал наблюдения механики (`debug` на EOF/завершение
  читателя; `warn` на ошибку записи и на detach по таймауту; `error` на ошибку
  `read` и на неудачу спавна потока). CLI/сокет/`main.rs`/`signal.rs` — ноль
  правок: ротация бессигнальна, не команда сокета, без флагов.

- **Взаимодействие с reload Этапа 8 — без правок reload-кода.** Изменение
  `[process.log]` при неизменном прочем попадает в `changed` через derived
  `PartialEq` у `ProcessConfig` → принудительный рестарт по существующей ветке
  `apply_config`; новый инстанс открывает pipe и потоки по новому конфигу.
  Убеждается тестом `changed_log_config_forces_restart`, а не декларацией.

- **Известные ограничения (осознанные).**
  1. Ротация только по размеру; по времени — не в v1 (кандидат POST_MVP).
  2. Без сжатия ротированных файлов (кандидат POST_MVP).
  3. Границы ротации — границы чанков `read()` (≤ 8 KiB), не строк: строка может
     разъехаться между `<path>.1` и текущим; текущий файл может превысить
     `max-size-bytes` на величину до одного чанка.
  4. Потомок, сбежавший из process-группы (собственный `setsid`) и держащий
     унаследованный stdout, оттягивает EOF; bounded join тогда детачит читателя
     (warn-лог), и до его завершения ротация старого и нового читателей одного
     пути не синхронизирована — тот же класс, что «сбежавший орфан переживает
     teardown» Этапа 4.
  5. `pipe()` без `O_CLOEXEC`: долгоживущие read-концы наследуются позже
     спавнящимися детьми и exec-пробами как лишние fd. На EOF и корректность не
     влияет; `pipe2(O_CLOEXEC)` потребовал бы фичи `fs` у `nix` при замороженном
     `Cargo.toml` — косметика.
  6. Ошибки записи лог-файла деградируют в потерю вывода с warn-логом и ленивым
     переоткрытием; чтение pipe не останавливается никогда (drain-first).
  7. Захваченный вывод буферизуется самим приложением: не-tty stdout у
     большинства stdio-рантаймов буферизуется блоками — забота приложения
     (`stdbuf`/line-buffering), не супервизора.
  8. Пути логов не видны в `status`/state-файле; смена `[process.log]` через
     reload — это рестарт процесса (сменить путь «на лету» без рестарта нельзя).
  9. Логи самого демона (`tracing`) не захватываются и не ротируются — этап
     касается только stdout/stderr супервизируемых процессов.
  10. Блокировка цикла на bounded join — до ~1 с в патологическом случае
      (детач-путь); нормальный случай — миллисекунды.

- **Границы правок.** `Cargo.toml`, `src/signal.rs`, `src/cli.rs`,
  `src/control.rs`, `src/health.rs`, `src/state.rs`, `src/clock.rs`, `src/main.rs`
  не изменены; схема state-файла не изменена; API `Clock`/`FakeClock` не
  расширен; механика process groups / teardown Этапа 4 не тронута (единственные
  вставки в `tick()` — вызов `join_log_readers` в ветке `Exited` и замена
  `process::spawn` → `start_instance` в респавн-ветке; плюс `join_log_readers` в
  `handle_poll_error`).

- **Критерий приёмки:** на живом демоне процесс с `[process.log]` и болтливым
  stdout наполняет `stdout-path`; при достижении `max-size-bytes` появляется
  `.1`, затем `.2`, но никогда больше `keep`; SIGTERM демону — exit 0, лог-файлы
  остаются на диске (в отличие от state-файла и сокета), state-файл и сокет
  удалены. ✅ — `tests/logs_e2e.rs::captured_output_rotates_end_to_end` (критерий
  целиком), `tests/logs.rs::rotation_happens_while_process_is_alive` (живая
  ротация, ретеншн ≤ keep), `output_is_complete_after_reap` и
  `deaf_tree_is_flushed_after_sigkill_escalation` (синхронная гарантия
  join-при-реапинге, включая SIGKILL-путь), `grandchild_output_is_captured`
  (захват дерева), `spawn_with_log_reaches_eof_after_child_exit` (фд-гигиена),
  `write_error_recovers_on_next_write` (drain-first),
  `concatenation_preserves_all_bytes` (целостность через ротации),
  `restarted_instance_appends_to_same_file` (append + счёт из metadata),
  `changed_log_config_forces_restart` (reload без правок reload-кода).
